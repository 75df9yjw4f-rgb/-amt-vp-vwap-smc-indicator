## 1. Исправление дефекта из P10

### Что было

`profFinalize()` — единственное место, где вычисляются `curProf.poc/vah/val` и выставляется `curProf.ready`. Оно было гейтировано расписанием **отрисовки** developing-линий:

```pine
bool devEnabled = showDevPoc and resolvedDevRecalc > 0        // Lite -> 0 -> false
bool devDue = devEnabled and (bar_index - curProf.startBar) % ... == 0
if curProf.bins > 0 and (devDue or barstate.islast)
    profFinalize(...)
```

В Lite это означало исполнение **только на последнем баре**.

### Что стало

Разделены две разные вещи: **когда считать** и **что рисовать**.

```pine
bool devEnabled = showDevPoc and resolvedDevRecalc > 0        // только ПЛОТЫ

int profRecalcEvery = switch perfMode                          // только ЛОГИКА
    PerfMode.lite     => 10
    PerfMode.standard => math.max(devRecalcEvery, 5)
    PerfMode.pro      => math.max(1, devRecalcEvery)

bool profDue = (bar_index - curProf.startBar) % math.max(1, profRecalcEvery) == 0
if curProf.bins > 0 and (profDue or barstate.islast)
    profFinalize(...)
    devPoc := curProf.poc      // значения поддерживаются всегда;
    devVah := curProf.vah      // плоты по-прежнему гейтируются devEnabled
    devVal := curProf.val
```

Lite по-прежнему пересчитывает реже остальных — в этом и смысл режима, — но теперь **всегда имеет значения**.

### Попутно исправлен второй, связанный дефект

`devPoc` использовался в AMT:

```pine
bool valueMigratedUp = not accNeedsMigration or (not na(devPoc) and not na(refHi) and devPoc > refHi)
```

В Lite `devPoc` был `na`, поэтому при включённом `Acceptance: require developing POC to migrate` **acceptance не срабатывал никогда**. Теперь `devPoc` поддерживается независимо от того, рисуются линии или нет, и это исправлено тем же изменением.

### Верификация — измерением, не утверждением

`tools/profile_sim.py` воспроизводит движок профиля (фиксированный шаг, add-only, классический VA) против тикового эталона:

```
mode              bins  model  recalc   POC err   stale  ready  ops/bar
                                        (ticks)  (bins)  (bar)
Lite (pre-fix)      24     M3      0b      0.79    0.00  299.0      7.4
Lite                24     M3     10b      0.79    0.04    0.0     12.2
```

- `ready` — бар, на котором `Profile.ready` впервые стал `true`. **299 → 0.** Дефект и его исправление измеримы.
- `stale` — среднее расхождение децимированного POC с точным, в бинах. **0.04 бина** — пренебрежимо.
- Цена исправления: **+4.8 операции на бар**.

## 2. Сравнение Lite / Standard / Pro

24 прогона × 300 баров × 60 внутрибарных тиков, процесс с возвратом к среднему (у чистого случайного блуждания профиль плоский, и POC у него определяется шумом — измерять там нечего).

```
mode              bins  model  recalc   POC err  VAL err  VAH err   POC err   stale  ready  ops/bar
                                         (bins)   (bins)   (bins)   (ticks)  (bins)  (bar)
Lite (pre-fix)      24     M3      0b      0.26     0.79     0.68      0.79    0.00  299.0      7.4
Lite                24     M3     10b      0.26     0.79     0.68      0.79    0.04    0.0     12.2
Standard            50     M3      5b      0.27     0.90     0.81      0.54    0.03    0.0     30.2
Pro (Bins=50)       50     M3      1b      0.27     0.90     0.81      0.54    0.00    0.0    109.9
Pro (Bins=150)     150     M3      1b      0.50     0.96     0.62      0.50    0.00    0.0    317.8
  24 bins / M1      24     M1     10b      0.62     0.40     0.74      1.88    0.03    0.0      6.0
  50 bins / M1      50     M1      5b      0.81     0.56     1.23      1.62    0.05    0.0     21.3
 150 bins / M1     150     M1      1b      1.38     0.71     0.79      1.38    0.00    0.0    301.0
```

### Что из этого следует

**1. Точность определяет модель распределения, а не число бинов.**
M3 даёт ошибку POC 0.50–0.79 тика при любом числе бинов. M1 — 1.38–1.88 тика, тоже при любом. Переход с M1 на M3 улучшает точность в **2.4 раза**; утроение числа бинов не улучшает почти ничего.

**2. Частота пересчёта не покупает точность.**
`Pro (Bins=50)` и `Standard` отличаются только каденцией (1 бар против 5) и имеют **идентичную ошибку** — 0.54 тика. Цена: 110 против 30 операций на бар. Децимация раз в 5 баров даёт расхождение 0.03 бина.

**3. Pro при дефолтных настройках почти не отличается от Standard.**
`Bins` по умолчанию = 50, а Pro не повышает его сам — он лишь снимает потолок. При `Bins = 50` Pro отличается от Standard только каденцией и лимитами профилей/зон. Разница появляется, когда пользователь **сам** поднимает `Bins`, и даже тогда 150 бинов дают 0.50 тика против 0.54 — за 10-кратную стоимость.

**4. Вывод: Standard — правильный дефолт.** Стоимость Pro покупает **детализацию уровней**, а не точность POC. Это честная формулировка того, за что платит пользователь.

> **Оговорка о применимости.** Это синтетический процесс с равномерным объёмом на тик. Относительное сравнение конфигураций информативно; абсолютные значения в тиках — не обещание для реального рынка.

## 3. Второе расхождение, найденное профилированием

Симуляция строилась по документации — и та не совпала с кодом.

`docs/03-architecture.md §3.5` утверждала, что Lite использует модель **M1**. В коде `distModel` **не резолвится режимом вообще** — берётся пользовательский input, по умолчанию **M3**. То же с источником данных, гистограммой, HVN/LVN, TPO и моделью направленного объёма.

### Что режим резолвит на самом деле

| Резолвится режимом | Не резолвится (отдельные переключатели) |
|---|---|
| `resolvedBins` | `distModel` — модель распределения |
| `resolvedProfiles` | `dataSrcIn` — **источник данных (L0–L3)** |
| `resolvedMaxZones` | `showHisto`, `showNodes`, `showTpo` |
| `profRecalcEvery` / `resolvedDevRecalc` | `deltaModelIn` |

Тултип режима при этом заявлял «bins, profile count, **rendering and data source**» — то есть UI обещал больше, чем код делает. Это тот же класс проблемы, что инертный input.

### Что сделано

- **Тултип исправлен** — теперь перечисляет ровно четыре управляемых параметра и прямо говорит, что модель, источник данных и отрисовка настраиваются отдельно **и именно они определяют нагрузку**. Изменение только строки, логика не тронута.
- **`docs/03-architecture.md §3.5` переписан** по факту, с измеренной стоимостью.

### Что НЕ сделано — и почему

**`Lite` не отключает L2 LTF.** Это самая дорогая подсистема: ≈250–350 операций на бар, то есть больше, чем всё остальное вместе. Одна строка сделала бы режим по-настоящему «лёгким»:

```pine
bool wantLtf = (dataSrcIn == DataSource.ltf or dataSrcIn == DataSource.auto)
     and perfMode != PerfMode.lite        // <- предлагаемое изменение
```

Не применено **сознательно**. Дефект `profFinalize` был исправлен потому, что он **молча отключал компонент** — это ошибка корректности. Гейтирование LTF режимом — изменение поведения, которое может быть нежелательным (пользователь вправе хотеть Lite-отрисовку с точными данными). Правило фазы — не менять логику без необходимости, а необходимости здесь нет: обходной путь очевиден и теперь написан в тултипе.

**Текущая рекомендация для минимальной нагрузки:** `Performance Mode = Lite` **плюс** `Profile data source = L1`.

## 9. Known Limitations

### Исправлено в P11

- ~~Децимация developing-профиля отключала VP-компонент на истории в Lite~~ → исправлено, проверено измерением.

### Действующие

1. **`Lite` не отключает L2 LTF** — самую дорогую подсистему. Обходной путь: `Profile data source = L1`. Одна строка сделала бы это автоматически; не применено, потому что это изменение поведения без необходимости (§3).
2. **Pro при дефолтном `Bins = 50` почти не отличается от Standard** по точности (0.54 тика у обоих) при 3.6× стоимости. Pro оправдан, только когда пользователь сам повышает `Bins`, и даже тогда покупает детализацию уровней, а не точность POC.
3. **Абсолютные цифры точности — синтетические.** Процесс с возвратом к среднему и равномерным объёмом на тик. Относительное сравнение информативно, абсолютные тики — нет.
4. **Симуляция моделирует только профильный движок.** Стоимость остальных подсистем оценена статически по коду, а не измерена.
5. Корреляция компонентов завышает `agreement` внутри confidence на ~10–20% в худшем случае (P8 §1.2).
6. Pivot lag `swingLen` баров наследуется цепочкой структуры и ликвидности (P10 §5.1).
7. Source drift на L2/L3 (P10 §5.7). Даже L3 — классификация по направлению цены, **не** bid/ask агрессор.
8. **Order Blocks / Breakers / Mitigation Blocks / Inducement — вне scope ACE v1.**
9. **Офлайн-компиляции Pine не существует.** K1/K2 и все графические тесты подтверждаются вами.
