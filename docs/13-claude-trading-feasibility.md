## 1. МОГУ ЛИ Я ПОЛУЧАТЬ ДАННЫЕ ACE В REAL TIME?

### 1.1 Что было проверено (а не предположено)

Я не стал предполагать, что TradingView «умеет отдавать данные». Проверено два источника:

1. **Исходный код ACE** — что он фактически экспортирует наружу.
2. **Актуальная документация TradingView** — что платформа фактически умеет подставлять
   в сообщение алерта и какие есть лимиты (ссылки в конце раздела).

### 1.2 Факт №1: в ACE нет ни одного `alert()`

В ACE v1 **28 вызовов `alertcondition()` и ноль вызовов `alert()`**.

Это не недочёт — это следствие принципа FACT vs INTERPRETATION, зафиксированного в
секции 16 самого ACE: алерты стоят только на фактах, и сознательно не стоят на
bias/confidence, потому что те зависят от пользовательских весов.

Но для нашей задачи у этого есть жёсткое техническое следствие:

> `alertcondition()` принимает **только константную строку**. Она физически не может
> нести вычисленные значения — ни Bias, ни Confidence, ни POC, ни уровни.

### 1.3 Факт №2: но у ACE есть 18 `plot()`, и плоты адресуемы из сообщения алерта

TradingView поддерживает в тексте сообщения плейсхолдеры `{{plot("Название")}}` и
`{{plot_0}}`…`{{plot_19}}` — **до 20 серий**, и это работает с `alertcondition()`
для Pine v4 и выше (ACE — v6).

ACE плотит ровно **18 серий** — то есть влезает в лимит 20 целиком:

| # | Название плота | Что это |
|---|---|---|
| 1–3 | `Developing POC` / `Developing VAH` / `Developing VAL` | развивающийся профиль |
| 4–9 | `Session/Daily/Weekly/Monthly VWAP`, `Anchored VWAP 1/2` | все VWAP |
| 10–13 | `VWAP +2σ` / `-2σ` / `+3σ` / `-3σ` | полосы |
| 14–17 | `BIAS`, `CONFIDENCE`, `BULL`, `BEAR` | **выход скоринга** (display = data_window) |
| 18 | `ACE anchor` | служебный, display = none |

### 1.4 Итог: что достижимо БЕЗ единой правки ACE

**✅ Достижимо сейчас (нулевое изменение ACE):**

- `Bias`, `Confidence`, `Bull`, `Bear` — весь числовой выход скоринга
- Весь VWAP-блок: session, daily, weekly, monthly, anchored 1/2
- Полосы VWAP ±2σ, ±3σ
- Developing POC / VAH / VAL
- Цена, объём, время, тикер, биржа, таймфрейм (`{{close}}`, `{{volume}}`, `{{time}}`,
  `{{timenow}}`, `{{ticker}}`, `{{exchange}}`, `{{interval}}`)
- **Факт наступления** 28 событий: BOS/CHoCH/MSS (bull/bear), sweep BSL/SSL, FVG up/dn,
  displacement up/dn, слом баланса, acceptance, rejection, кроссы VWAP/бэндов/VAH/VAL/POC,
  imbalance stack, unfinished auction

**❌ НЕ достижимо без правки ACE:**

| Требуемое вами | Почему недоступно |
|---|---|
| Component Contributions (по каждому компоненту: score/weight/state) | не плотится, живёт только в таблице дашборда |
| WHAT CHANGED | текст дашборда, не плот |
| Статические POC / VAH / VAL (`curProf`) | плотится только **developing**, не закрытый профиль |
| Уровни структуры, цены свингов, уровень BOS/CHoCH/MSS | событие есть, **цена уровня — нет** |
| Уровни ликвидности, цена свипа | то же самое |
| Границы FVG | то же самое |
| AMT: диапазон баланса, магнитуда acceptance | то же самое |
| Order Flow: delta, стеки, unfinished | то же самое |
| L1/L2/L3 — какой слой данных реально активен | не плотится |
| Полоса ±1σ | не плотится (есть только ±2σ и ±3σ) |

Формулируя честно: **числовой «мозг» ACE (скоринг) и вся геометрия VWAP/Value
экспортируются без единой правки. Весь структурный слой экспортируется как «событие
произошло», но без цены, на которой оно произошло.**

Торговать по «BOS произошёл, уровень неизвестен» нельзя — от уровня зависит и вход, и стоп.

### 1.5 Как получить периодический снимок, не трогая ACE: ACE-Bridge

Проблема: `alertcondition()` привязан к условию. В ACE нет условия «всегда истина»,
поэтому **периодический снимок каждую свечу из ACE получить нельзя** — он бы требовал
нового `alert()` внутри ACE, что вы запретили.

Решение, не нарушающее запрет: **отдельный индикатор-мост `ACE-Bridge.pine`**, который
не является частью ACE и ничего в ACE не меняет.

```pine
//@version=6
indicator("ACE Bridge", overlay = true)

// Каждый вход вручную привязывается в настройках к соответствующему плоту ACE.
float bias = input.source(close, "ACE: BIAS")
float conf = input.source(close, "ACE: CONFIDENCE")
float poc  = input.source(close, "ACE: Developing POC")
// ... и так далее по нужным плотам ACE

// alert() допускает ВЫЧИСЛЯЕМУЮ строку и лимит 40960 символов.
alert(str.format('{{"bias":{0},"conf":{1},"poc":{2},...}}', bias, conf, poc),
     alert.freq_once_per_bar_close)
```

`input.source()` умеет ссылаться на плот **другого** индикатора на том же графике.
Это даёт:

- периодический снимок на каждом закрытии бара (heartbeat), а не только по событиям;
- лимит сообщения **40960 символов** вместо 4000 (лимит `alert()` против лимита поля
  «Сообщение» в диалоге);
- полностью вычисляемый JSON.

Ограничение остаётся ровно одно, и оно принципиальное: **мост видит только то, что ACE
плотит.** 18 серий. Структуру, ликвидность, FVG, AMT и order flow он не увидит, потому
что их там нет.

> ⚠️ Проверить в UI: плоты с `display = display.data_window` (BIAS, CONFIDENCE, BULL,
> BEAR) должны быть доступны в выпадающем списке `input.source`. Плот с
> `display = display.none` (`ACE anchor`), скорее всего, недоступен. Это проверяется
> за две минуты в настройках и я это не проверял — у меня нет доступа к вашему графику.

### 1.6 Три возможных пути — выбор за вами

| Путь | Что даёт | Цена |
|---|---|---|
| **A. ACE-Bridge** (рекомендую начать здесь) | Bias/Confidence/VWAP/Developing VA каждую свечу + 28 событий-фактов | ACE не тронут. Структура/ликвидность/FVG/AMT — без уровней |
| **B. Один additive `alert()` в ACE** | Полный снимок: контрибуции, WHAT CHANGED, все уровни, L1/L2/L3 | **Требует правки ACE — вы это запретили.** Правка аддитивная: один вызов, скоринг не трогается. Решение ваше |
| **C. Порт ACE в Python** | Полный контроль, реплей, бэктест, никакой зависимости от вебхуков | Недели работы + обязательство доказать паритет с Pine-версией |

Честная рекомендация: **A для прототипа, C для чего-либо серьёзного.** B — это компромисс,
который стоит рассмотреть только если вы согласитесь, что «один `alert()` в конце файла,
не трогающий ни один расчёт» — это не нарушение заморозки scope. Я не принимаю это решение
за вас.

**И отдельно, важное:** чего TradingView не умеет вообще, ни при каком плане —
**pull-запроса**. Нет API «дай мне текущее состояние индикатора». Только push, только по
событию, только строкой. Из этого следует вся дальнейшая архитектура: система
**event-driven, а не polling**, и она обязана переживать потерю события.

### 1.7 Чего в TradingView нет вообще и что придётся брать в другом месте

| Данные | Откуда брать |
|---|---|
| Текущая цена между барами | API биржи/брокера (WebSocket) |
| Состояние позиции | API брокера — **единственный источник истины** |
| Предыдущие решения | ваш State Store |
| Результат предыдущей сделки | API брокера + ваш журнал |
| Стакан, спред, ликвидность на исполнение | API брокера |

## 2. МОГУ ЛИ Я ПРИНИМАТЬ ТОРГОВОЕ РЕШЕНИЕ?

### 2.1 Да — но я не то, чем меня обычно считают

Самое важное, что я должен сказать прямо, потому что вы это прямо и просили не
предполагать:

> **Я не постоянно работающий процесс.** У меня нет фонового исполнения, нет таймера,
> нет памяти между вызовами, нет гарантии доступности. Я — функция: приходит запрос,
> уходит ответ. Между вызовами меня не существует.

Из этого следует всё остальное в этом документе. Цикл, который вы нарисовали, **реален**,
но замыкает его не Claude, а внешний процесс. Я в нём — один шаг, а не двигатель.

### 2.2 Цикл, который реально работает

```
Закрытие бара в TradingView
   ↓  alert → webhook (push, без гарантий)
Receiver: ACK < 3 сек, кладёт в очередь          ← обязательно, см. §6
   ↓
Orchestrator (постоянный процесс — ЭТО двигатель цикла)
   ├── дополняет снимок: цена, позиция, история решений (из брокера и State Store)
   ├── проверяет свежесть и целостность (gap detection)
   ↓
Claude: один вызов, один снимок → одно решение в JSON
   ↓
Risk Engine (отдельный код, право вето)
   ↓
Execution Engine → брокер (вход + защитный стоп одной транзакцией)
   ↓
Результат исполнения → State Store → следующий снимок
```

### 2.3 Могу ли я анализировать контекст, а не набор стрелок

Да, и это, вероятно, единственное место, где я в принципе могу добавить что-то поверх
механического правила. Мне естественно даётся:

- собрать разнородные факты в одну связную картину («цена вышла за VAH, но объём падает,
  а VWAP остался ниже — принятия нет, есть вынос»);
- заметить **несогласованность** между компонентами, а не просто сложить их веса;
- учесть WHAT CHANGED как отдельный сигнал — изменилось ли что-то, или это тот же контекст,
  что и час назад;
- отказаться от сделки, потому что картина противоречива — а не потому, что порог не пройден.

Но — и это надо сказать в том же абзаце — **я не умею считать вероятности.** Когда я
говорю «высокая уверенность», за этим не стоит откалиброванного распределения. Это
языковая формулировка, а не статистика. Ровно та же оговорка, которую вы сами потребовали
для ACE Confidence («internal model agreement, НЕ вероятность»), применима ко мне в полной
мере, и в моём случае она даже сильнее: у ACE хотя бы есть детерминированная формула.

### 2.4 Чего я в этом цикле делать не должен

| Не должен | Почему |
|---|---|
| Хранить состояние | между вызовами меня нет; состояние потеряется молча |
| Управлять позицией в реальном времени | между барами меня никто не вызывает |
| Считать размер позиции в деньгах | арифметика на капитале — не то, что стоит доверять языковой модели |
| Быть в пути защитного стопа | если я недоступен — позиция окажется голой |
| Повторять ордера при ошибке | дубликаты; retry — задача Execution Engine с идемпотентностью |
| Выбирать инструмент/счёт | расширение поверхности атаки; это конфиг, а не решение |

## 3. ЧТО ИМЕННО Я ДОЛЖЕН ВЫДАВАТЬ

Ваш черновой формат правильный по духу, но в нём три дыры, которые на реальных деньгах
стоят денег. Предлагаю строгую схему.

### 3.1 Три исправления к вашему формату

1. **`POSITION SIZE` убрать.** Я выдаю риск в единицах **R** (доля риска на сделку),
   а размер считает Risk Engine из актуального капитала. Так я физически не могу
   ошибиться в размере — я его не вычисляю.
2. **`LONG/SHORT/HOLD` недостаточно.** Этими тремя словами нельзя выразить «сократить
   половину», «перенести стоп в безубыток», «закрыть». Нужен отдельный `intent`.
3. **Нужен срок годности.** Решение, принятое на закрытии бара, через 4 минуты может быть
   опасным. Нужны `valid_until` и ценовой коридор, вне которого решение аннулируется.

### 3.2 Схема решения

```json
{
  "schema_version": "1.0",
  "decision_id": "uuid",
  "idempotency_key": "sha256(symbol|bar_close_time|decision_seq)",
  "as_of_bar_close": "2026-09-14T15:00:00Z",
  "snapshot_hash": "sha256(входной снимок)",

  "action":  "LONG | SHORT | FLAT | NONE",
  "intent":  "OPEN | ADD | REDUCE | CLOSE | MOVE_STOP | NONE",

  "entry": { "type": "MARKET | LIMIT | STOP", "price": 64250.0,
             "valid_until": "2026-09-14T15:04:30Z",
             "price_band": [64180.0, 64320.0] },

  "stop":    { "price": 63900.0, "basis": "под свингом 63950 + 0.5 ATR" },
  "targets": [ { "price": 64900.0, "fraction": 0.5, "basis": "VAH предыдущего профиля" },
               { "price": 65600.0, "fraction": 0.5, "basis": "верхняя полоса VWAP +2σ" } ],

  "risk_r": 0.5,
  "max_holding_bars": 24,

  "invalidation": [
    { "type": "price_below", "value": 63900.0 },
    { "type": "ace_event",   "value": "CHOCH_DOWN" },
    { "type": "time",        "value": "2026-09-14T22:00:00Z" }
  ],

  "ace_bias": 0.42,
  "ace_confidence": 0.61,
  "facts_used": ["bias", "confidence", "developing_vah", "session_vwap", "event:FVG_UP"],
  "self_confidence": "low | medium | high",
  "abstain_reason": null,

  "reason": "Свободный текст. Не парсится ничем. Только для журнала и разбора."
}
```

### 3.3 Правила, которые делают схему безопасной

- **`stop` обязателен.** `null` → схема невалидна → Risk Engine отклоняет. Без исключений.
- **По умолчанию — отказ.** Любая ошибка парсинга, любое отсутствующее поле, любое
  значение вне диапазона → `action: NONE`. Система fail-safe, не fail-open.
- **`facts_used` проверяется машинно.** Если я сослался на факт, которого не было во
  входном снимке, — решение отклоняется автоматически. Это прямая защита от того, что я
  сошлюсь на то, чего не видел. Дешёвый и очень действенный механизм.
- **`risk_r` ограничен сверху конфигом**, не мной.
- **`reason` не влияет ни на что.** Ни одно поле исполнения не извлекается из
  свободного текста. Текст — для человека.
- **`idempotency_key` сквозной** до брокера: один бар → максимум один ордер, сколько бы
  раз сообщение ни продублировалось.

## 4. CLAUDE VS TRADING BOT

### 4.1 Ваша архитектура — правильная

> ACE = Market Context Engine · Claude = Decision Engine · Bot = Execution Engine ·
> Risk Engine = защита капитала · Broker = исполнение

Это **корректное разделение ответственности**, и оно корректно именно по той причине,
по которой строился сам ACE: разделение факта и интерпретации. ACE выдаёт факты, я выдаю
интерпретацию, Risk Engine не доверяет ни тому, ни другому, а исполнение вообще не знает,
откуда взялось решение.

Добавить нужно четыре компонента, которых в вашей схеме нет и без которых она разваливается
на второй неделе:

| Компонент | Зачем |
|---|---|
| **State Store** | позиции, решения, сделки, снимки. Моя память живёт здесь, потому что у меня её нет |
| **Reconciliation** | периодическая сверка «что я думаю о позиции» ↔ «что реально у брокера». Расхождение → kill switch |
| **Audit Log** | неизменяемый журнал: снимок → промпт → ответ → вердикт риска → ордер → исполнение. Без него разбор невозможен |
| **Dead-man switch** | если Orchestrator умер, защита позиции должна пережить его смерть |

### 4.2 Единственный принцип, который нельзя нарушать

> **Защита позиции не должна зависеть ни от меня, ни от сети, ни от вашего сервера.**

Стоп — это **резервный ордер на стороне брокера**, выставленный одной транзакцией со
входом (OCO / bracket). Не «Claude решит закрыть», не «бот проверит на следующем баре».

Если стоп живёт в вашем коде, то отключение электричества у вас дома = позиция без защиты.
Это не теоретический риск, это самый обычный сценарий.

## 5. МОЖЕТ ЛИ ЭТО БЫТЬ ПОЛНОСТЬЮ АВТОНОМНО?

### 5.1 Прямой ответ

**Может ли Claude работать без подтверждения человека?** — Да, технически может: ни один
шаг цикла не требует человека в реальном времени.

**Может ли Claude сам быть этой автономностью?** — **Нет.** И это не ограничение
осторожности, это факт архитектуры: я не запускаюсь сам, не просыпаюсь по таймеру и не
существую между вызовами.

Автономен **цикл**. Я — шаг внутри цикла.

### 5.2 Что обязано работать постоянно, кроме меня

| Сервис | Обязателен | Что делает |
|---|---|---|
| Webhook Receiver | да | принимает push, отвечает < 3 сек, кладёт в очередь |
| Queue | да | развязывает приём и обработку |

### 6.2 Три следствия, которые определяют архитектуру

**Следствие 1: меня нельзя вызывать внутри обработчика вебхука.**
Мой ответ занимает секунды-десятки секунд, таймаут — 3 секунды. Синхронный вызов будет
падать по таймауту **всегда**. Отсюда обязательная схема: принять → подтвердить →
в очередь → обработать асинхронно. Это не оптимизация, это единственный рабочий вариант.

**Следствие 2: сигналы будут теряться.**
Доставка без гарантий и без ретраев. Значит обязательны:
- сквозной `seq` в каждом сообщении и **детектор пропусков**;
- независимый источник цены для сверки;
- поведение при пропуске: **не догонять задним числом**, а пересобрать актуальное
  состояние. Отработка устаревшего сигнала хуже пропущенного.

**Следствие 3: сообщения будут дублироваться.**
Отсюда идемпотентность по `sha256(symbol|bar_close_time|seq)` на всём пути до брокера.

### 6.3 Бюджет времени по таймфреймам

| ТФ | Бюджет на бар | Вердикт |
|---|---|---|
| 1m | 60 с | 🟡 впритык; при деградации API — срыв цикла |
| 5m | 300 с | 🟢 комфортно |
| 15m+ | 900 с+ | 🟢 с большим запасом |
| < 1m | — | 🔴 не рассматривать |

Типичная раскладка на 5m: вебхук 1–3 с → очередь <1 с → сбор снимка 1–2 с → **Claude
2–20 с** → риск <1 с → ордер 0.1–2 с. Итого ~5–30 с из 300. Запас десятикратный, и он
нужен целиком: он тратится на ретраи, деградацию и всплески задержек.

### 6.4 Отказы и реакция

| Событие | Реакция (обязательная) |
|---|---|
| Потеря связи с TradingView | новые входы запрещены; **стопы у брокера уже стоят** и работают |
| Ошибка/недоступность Claude | `action: NONE`. Никогда не «решить самому» по запасному правилу |
| Таймаут Claude | отменить вызов; бар пропущен; это нормальный исход |
| Невалидный JSON от Claude | отклонить. Один ретрай с ужесточённой инструкцией, потом отказ |
| Ошибка брокера при входе | не ретраить вслепую → сверка → если позиции нет, вход отменён |
| Ошибка брокера при выставлении стопа | **немедленно закрыть позицию по рынку.** Позиция без стопа не живёт ни секунды |
| Расхождение позиции при сверке | kill switch + уведомление человека. Автоматически не «чинить» |
| Смерть Orchestrator | dead-man switch; брокерские стопы переживают его |

Обратите внимание на асимметрию: **все пути отказа ведут к «ничего не делать» или
«закрыться», и ни один — к «попробовать угадать».**

## 7. RISK ENGINE

### 7.1 Принцип

> **Мой вывод — это недоверенный ввод.** Ровно того же класса, что строка от пользователя
> из интернета. Risk Engine не «проверяет корректность решения Claude» — он защищает
> капитал от любого источника команд, включая меня.

Практически это значит: отдельный модуль, отдельный конфиг-файл, права только на чтение
конфига из процесса решения, **никакого пути, которым я мог бы изменить лимиты** — ни
через вывод, ни через промпт, ни через «обоснование». Лимиты не аргументируются.

### 7.2 Обязательные проверки

**Капитал:** риск на сделку (жёсткий потолок `risk_r`), дневной убыток, недельный убыток,
максимальная просадка, максимальный размер позиции, максимальное плечо, максимальное
число одновременных позиций, экспозиция по коррелированным инструментам.

**Ордер:** стоп обязателен; стоп по правильную сторону от входа; расстояние до стопа в
допустимом коридоре; ценовой коридор от рынка (защита от «толстого пальца»); максимальный
номинал; максимальный спред; максимальный slippage; частота ордеров в минуту.

**Данные:** возраст снимка (устаревший — отказ); совпадение `snapshot_hash`; дубль
`idempotency_key`; факты из `facts_used` присутствуют в снимке.

**Режим:** торговая сессия; запрет на входы за N минут до закрытия; блэкаут вокруг
новостей (если заведён календарь); cooldown после убытка; cooldown после серии убытков.

**Аварийные:** kill switch (ручной, мгновенный, из любой точки); auto-kill по просадке;
emergency close всего; dead-man switch по «тишине» Orchestrator.

### 7.3 Правило по умолчанию

Любая проверка, которая **не смогла выполниться** (нет данных о капитале, недоступен
брокер, не читается конфиг), считается **непройденной**. Отказ — дефолтный исход, разрешение —
исключение, требующее, чтобы все проверки явно прошли.

## 8. КАК ПРОВЕРИТЬ, ЧТО Я ДЕЙСТВИТЕЛЬНО УМЕЮ ТОРГОВАТЬ

Ваша лестница правильная. Добавляю критерии перехода — и предупреждение о размере выборки,
без которого все критерии бессмысленны.

### 8.1 Предупреждение о выборке (читать до критериев)

На 30 сделках **нельзя** отличить систему с ожиданием +0.1R от системы с ожиданием −0.1R.
На 100 сделках нельзя надёжно отличить winrate 50% от 55%. Чтобы уверенно детектировать
небольшое преимущество, нужны **сотни** сделок, и на 5m это месяцы.

Любой вывод «работает!» раньше этого — не вывод, а шум. Это главный способ, которым люди
теряют деньги на автоматизации: принимают удачную серию за подтверждение.

### 8.2 Лестница

| Шаг | Что делаем | Критерий перехода дальше |
|---|---|---|
| **1. Historical research** | реплей истории, снимки строго на закрытии бара | Воспроизводимость 100%: один снимок → одно решение. Без этого дальше нельзя |
| **2. Replay / simulated realtime** | прогон в темпе, с задержками и пропусками | ≥200 решений; 0 нарушений lookahead при аудите; 0 обращений к данным, которых не было в снимке |
| **3. Paper trading** | биржевой paper-счёт, реальный фид | ≥100 сделок; expectancy > 0 после издержек; 0 нарушений риск-правил; 0 ордеров без стопа |
| **4. Shadow trading** | решения принимаются, **ордера не отправляются**, всё журналируется | ≥1 месяц; ≥100 решений; расхождение с paper-исполнением объяснимо; **преимущество над механическим baseline статистически значимо** |
| **5. Paper execution + real feed** | полный путь, реальные задержки, симулированное исполнение | ≥1 месяц; slippage в модели; 0 инцидентов рассинхрона; система пережила ≥1 сбой без потери защиты |
| **6. Минимальные реальные деньги** | сумма, потерю которой вы примете спокойно целиком | Только после 4 и 5. Не «после 3». |

**Жёсткое правило для шага 6:** размер = сумма, полную потерю которой вы заранее приняли.
Не «рискованная, но приемлемая» — **полная потеря**. Если такой суммы нет — шаг 6 не наступает.

## 9. КАК ИЗМЕРЯТЬ КАЧЕСТВО

### 9.1 Метрики

**Результат:** expectancy (R/сделку — главная), Profit Factor, winrate, средний
выигрыш/проигрыш, max drawdown, Sharpe, Sortino, число сделок, среднее время в позиции.

**Исполнение:** slippage (план vs факт), ошибки исполнения, пропущенные сделки,
отклонения Risk Engine, нарушения риска (обязано быть 0).

**Качество решений:** доля отказов от сделки; доля решений с невалидной схемой;
доля решений, сославшихся на отсутствующие факты; согласованность (один снимок дважды →
одинаковое решение?); разбивка по рыночным режимам (тренд / баланс / высокая и низкая
волатильность).

### 9.2 Протокол сравнения — это и есть главный тест

Все baseline гоняются **на тех же самых точках решения, с теми же издержками**:

1. `sign(ACE Bias)` — простейшее правило
2. ACE Bias + порог Confidence
3. фиксированная ACE-стратегия (например: вход по BOS в сторону bias при цене вне Value)
4. baseline VWAP (возврат к VWAP)
5. baseline breakout (пробой Value Area)
6. baseline mean reversion (от полос ±2σ)

Сравнивать **попарно на одних и тех же барах**, считать доверительный интервал **разницы**
(bootstrap), а не абсолютных результатов каждого.

### 9.3 Порог, который я предлагаю себе самому

> Если я не обыгрываю лучший механический baseline на величину, значимую после издержек и
> стоимости API-вызовов, — **я в этой системе лишний.**

И это нормальный, честный исход. В этом случае правильный продукт — детерминированная
стратегия на ACE: дешевле, быстрее, воспроизводима, не требует ничего из §5–§7.
Этот исход надо считать вероятным заранее, а не «поражением».

## 10. КАК НЕ ДАТЬ МНЕ ОБМАНУТЬ САМОГО СЕБЯ

### 10.1 Самая серьёзная проблема — и она специфична именно для LLM

> **Я обучен на данных, которые включают исторические рынки.**

Если вы дадите мне бары BTC за март 2024 и спросите решение, я могу «знать», что было
дальше — не из снимка, а из обучения. Это **утечка будущего, которую невозможно убрать
промптом.** Никакая инструкция «не используй знание будущего» не решает проблему, потому
что это не сознательное обращение к знанию.

Это делает наивный исторический бэктест LLM-решений **принципиально ненадёжным**.

Меры (ослабляют, не устраняют):
- обезличить инструмент: убрать тикер, даты, абсолютные цены; подавать нормализованные величины;
- использовать период **после** даты отсечения обучения;
- главный вес переносить на **shadow и forward** тестирование, а не на историю;
- считать шаг 1 лестницы проверкой корректности механики, **а не оценкой прибыльности**.

### 10.2 Наследование честности ACE

ACE уже задокументировал четыре категории (repaint / lag / backpainting / source drift).
Они не исчезают — они наследуются системой:

| Категория | Как проявится здесь | Мера |
|---|---|---|
| Pivot lag | свинги подтверждаются через `swingLen` баров | снимок помечает уровень как подтверждённый/неподтверждённый; на неподтверждённых входа нет |
| Sweep confirmation | режим подтверждения через CHoCH даёт задержку | в снимок передаётся статус подтверждения, а не факт |
| Developing profile | POC/VAH/VAL меняются внутри периода | явно помечать «developing», не «final» |
| Source drift | L3 доступен не всегда | снимок несёт реальный слой данных; смена слоя = смена смысла |
| Backpainting | событие отрисовано на прошлом баре | в снимке всегда время **обнаружения**, а не время события |

**Правило снимка:** каждый факт несёт `confirmed: true|false` и `as_of`. Я обязан
игнорировать неподтверждённое при входе.

### 10.3 Остальные ловушки

| Ловушка | Мера |
|---|---|
| Lookahead в харнессе | снимок строится только из данных ≤ времени закрытия бара; отдельный аудит |
| Selection bias | не выбирать «удачные» периоды; тестировать подряд |
| Survivorship bias | делистнутые/умершие инструменты не исключать |
| Overfitting промпта | **промпт — это параметр.** Версионировать, вести журнал изменений, держать held-out период |
| Hindsight reasoning | запретить формулировки «здесь был очевидный лонг»; проверять `facts_used` машинно |
| Подгонка параметров ACE | параметры ACE фиксируются **до** тестов и не трогаются по результатам |

### 10.4 Самая незаметная ошибка

**Каждая правка промпта после просмотра результатов сжигает out-of-sample.** Через двадцать
итераций «улучшений» вы получите промпт, подогнанный под конкретный период, и никакого
способа это заметить — потому что «тест» вы уже видели.

Единственная защита: отложенный период, к которому вы не прикасаетесь до финальной
проверки, и журнал версий промпта с датами.

## 11. МОГУ ЛИ Я САМ УЛУЧШАТЬ ТОРГОВЛЮ

### 11.1 Как аналитик — да

Разбор собственного журнала сделок — то, что я делаю хорошо: найти повторяющиеся ошибки,
плохие режимы рынка, неудачные комбинации факторов ACE, систематически ранние или поздние

### 11.2 Как автор изменений в продакшене — нет

Ваше ограничение абсолютно верное, и я его усилю:

> Ни одно изменение стратегии не применяется автоматически. Никогда. Ни при каком
> количестве убыточных сделок.

Причины: серия из 5–10 убытков **статистически ожидаема** у прибыльной системы; реакция на
неё — гарантированный способ сломать работающее. Плюс замкнутый контур «я анализирую свои
решения → я меняю свои правила → я анализирую результат своих изменений» не имеет внешней
точки опоры и уходит в дрейф.

### 11.3 Разрешённый контур

```
Журнал сделок → Claude-аналитик → ГИПОТЕЗА (не изменение)
   ↓
Формализация в проверяемое правило
   ↓
Бэктест + shadow на отложенном периоде
   ↓
Минимальный размер выборки достигнут?  — нет → гипотеза ждёт
   ↓ да
РЕШЕНИЕ ЧЕЛОВЕКА
   ↓
Версионированное изменение промпта/политики → shadow → промоут
```

Обязательное условие: минимальный размер выборки **на гипотезу**, объявленный заранее.
«Три сделки подряд убыточные после FVG» — это не находка, это шум.

## 12. ГЛАВНЫЙ ВОПРОС — ЧЕТЫРЕ ЧЕСТНЫХ ОТВЕТА

### 12.1 Может ли Claude технически быть автономным decision engine для ACE?

**Как компонент — да. Как автономная сущность — нет.**

Я могу принимать решения по снимку и возвращать строгий JSON. Я не могу быть тем, что
крутит цикл: у меня нет ни фонового исполнения, ни памяти, ни гарантии доступности.
Автономен цикл, который вы построите вокруг меня. Без Orchestrator, State Store и Risk
Engine автономности нет вообще — есть человек, вручную копирующий данные в чат.

### 12.2 Может ли Claude участвовать в полном цикле DATA → ANALYSIS → DECISION → ORDER → POSITION MANAGEMENT?

**Да — в первых трёх звеньях, и только косвенно в последних двух.**

DATA — да (получаю снимок). ANALYSIS — да. DECISION — да, в виде строгой схемы.
ORDER — **нет, я не отправляю ордера**; я выдаю намерение, которое проходит вето Risk
Engine и исполняется отдельным сервисом. POSITION MANAGEMENT — частично: я могу на
следующем баре сказать «сократить/перенести стоп», но **защита позиции между барами
обязана работать без меня**, брокерскими резервными ордерами.

### 12.3 Что конкретно нужно построить?

| # | Компонент | Оценка |
|---|---|---|
| 1 | `ACE-Bridge.pine` — мост через `input.source` + `alert()` | 1–2 дня |
| 2 | Webhook Receiver (ACK < 3 с) + очередь | 2–3 дня |
| 3 | Snapshot Builder (снимок + `confirmed`/`as_of` + хэш + `seq`) | 3–5 дней |
| 4 | State Store (схема + миграции) | 2–3 дня |
| 5 | Claude Decision Service (промпт, схема, валидация, проверка `facts_used`) | 5–8 дней |
| 6 | **Risk Engine** (отдельный модуль, тесты на каждое правило) | 5–8 дней |
| 7 | Execution Engine (идемпотентность, bracket-ордера, ретраи, сверка) | 8–12 дней |
| 8 | Position Monitor + Reconciliation | 4–6 дней |
| 9 | Replay/Backtest harness + аудит lookahead | 8–12 дней |
| 10 | Метрики и baseline-сравнение | 4–6 дней |
| 11 | Мониторинг, алертинг, kill switch, dead-man | 4–6 дней |

IPv6-only; БД; мониторинг.

### 12.4 Есть ли основания ожидать прибыльность?

**Нет. Ни одного — кроме надежды.**

Разделяю явно, как вы и просили:

**TECHNICAL FEASIBILITY — 🟢 высокая.** Всё описанное строится известными средствами.
Рисков реализации мало, они понятны.

**TRADING PROFITABILITY — 🔴 нет оснований ожидать.** По пунктам:

1. **Преимущество самого ACE не доказано.** ACE — движок контекста. Он ни разу не
   проверялся статистически на предсказательную силу. Мы не знаем, есть ли что-то, поверх
   чего можно строить. Это фундамент, и он непроверен.
2. **У меня нет продемонстрированного преимущества в рыночном тайминге.** Я хорошо работаю
   с текстом и структурой, я связно рассуждаю о контексте — но связное рассуждение о рынке
   и прибыльные решения о рынке это **разные вещи**, и вторая не следует из первой.
   Убедительность объяснения не является свидетельством его правильности.
3. **Издержки определённы, преимущество — нет.** Спред, комиссия, slippage, фандинг и
   стоимость вызовов API вычитаются из результата с вероятностью 100%. Преимущество —
   гипотеза.
4. **Канал проверки на истории заражён** (§10.1). Самый дешёвый способ проверки для меня
   работает хуже всего.
5. **Рынок — соревновательная среда.** Против вас работают участники с несопоставимыми
   данными, латентностью и капиталом. «Я рассуждаю о контексте» не является преимуществом
   перед ними.
6. **Отсутствие калибровки.** Моя «высокая уверенность» не откалибрована. Это делает
   любой размер позиции, зависящий от моей уверенности, необоснованным.

**Что при этом честно сказать в пользу проекта:** вы строите **измерительный аппарат**.
