## Что реализовано

### Ядро: add-only накопление с фиксированным шагом

Главное архитектурное решение P1 — **шаг бина фиксируется при открытии периода и никогда не меняется**. Когда цена выходит за сетку, сетка **расширяется пустыми бинами** (`array.unshift` / `array.push`), а существующие бины сохраняют содержимое байт-в-байт.

Почему это важно:
- **нет перераспределения** → нет накопления ошибки округления;
- стоимость бара — `O(бинов, задетых баром)` ≈ 1–20, а не `O(баров × бинов)`;
- developing POC/VA становятся дешёвыми: это просто `O(bins)` поверх готового накопителя.

Расширение ограничено `binCapHard = min(500, bins × 4)`. При упоре в потолок ставится флаг `clamped`, и **дашборд говорит об этом отдельной жёлтой строкой** вместо того, чтобы молча класть хвосты не в те бины.

### Реализованный функционал

| Требование | Статус | Детали |
|---|---|---|
| configurable bins | ✅ | 10–500, потолок по режиму (Lite 24 / Standard 150 / Pro без ограничения) |
| POC | ✅ | детерминированное разрешение ничьей: ближайший к цене бин, затем меньший индекс |
| VAH / VAL | ✅ | границы крайних включённых бинов |
| Value Area % | ✅ | 1–100, по умолчанию 70 |

| HVN / LVN | ✅ | локальные экстремумы в окне `nodeWin`, нормировка на максимум бина |
| developing POC/VAH/VAL | ✅ | декимация `resolvedDevRecalc`; в Lite отключены; `plot.style_linebr` — не мостит через границу периода |
| current session profile | ✅ | якорь Session/Daily/Weekly/Monthly/Fixed |

### Дополнительно (сверх минимума P1)

- **`maxBinsPerBar`** — предохранитель: бар, покрывающий больше N бинов (гэп, аномальная свеча), откатывается на close-only и помечает профиль `clamped`. Без этого один аномальный бар мог бы съесть весь бюджет цикла.
- **Раздельный up/down объём по бинам** (`volUp`/`volDn`) — уже накапливается из Δ-proxy, готово к Delta Profile в P7.
- **Компонент VP подключён к scoring** — первая сквозная проверка всего конвейера: FACT → Context → Score → Dashboard.

### FACT, который отдаёт движок

`POC` · `VAH` · `VAL` · `bins` · `step` · `lo/hi` · `total` · `tpoTotal` · `clamped` · `model` · **`valuePos`** (непрерывная позиция цены в структуре стоимости) · `valueState` (текстовое состояние).

`valuePos` — именно **измерение**, а не оценка:
- внутри VA: `(close − POC) / (VAH − VAL)`, ограничено `±0.5`;
- выше VAH: `+0.5 … +1.0`, насыщение на половине ширины VA за границей;
- ниже VAL — зеркально.

Решение «бычье это или медвежье» принимает Context Engine, а не Profile Engine. Инвариант #1 соблюдён.

## ⚠️ Сравнение с нативным Volume Profile TradingView

Вы просили провести это сравнение. **Провести его я не могу — в этой среде нет ни TradingView, ни рыночных данных.** Ниже — протокол, который выполняете вы, и мой прогноз расхождений с объяснением причин. Когда пришлёте фактические цифры, разберу отклонения.

### Протокол
1. Инструмент с надёжным объёмом: `CME_MINI:ES1!` или `BINANCE:BTCUSDT`.
2. ТФ: 5m, 15m, 1H. Якорь профиля: `Session / Day`.
3. Рядом — встроенный TradingView `Volume Profile Visible Range` либо `Session Volume Profile`, Value Area 70%.
4. Сверить на 5 завершённых сессиях: POC, VAH, VAL.
5. Зафиксировать отклонение в **бинах** (не в тиках): `|наш − нативный| / step`.

### Прогноз и причины расхождений

| Метрика | Ожидаемое отклонение | Причина |
|---|---|---|
| **POC** | 0–1 бин | Разные источники: у нас распределение барного объёма (M3), у TradingView — серверные интрабарные данные. POC — argmax, поэтому он «перескакивает» между соседними бинами при близких объёмах |
| **VAH / VAL** | 1–2 бина | Наследуют сдвиг POC, плюс дискретизация парного расширения |
| **Форма гистограммы** | визуально близка | Основные кластеры совпадают; хвосты у нас глаже из-за модели M3 |
| **Ширина VA** | ±5% | Зависит от шага бина и границ сетки |
| **На 1m и ниже** | расхождение растёт | Бар покрывает 1–3 бина, распределять почти нечего — M3 вырождается в M1 |
| **На 1D и выше** | расхождение растёт заметно | Один бар = огромный диапазон; без L2/L3 модель распределения груба. Плюс на TF ≥ 1D EOD-фиды включают блочные и OTC-сделки |

### Чего мы делать НЕ будем

**Подгонять алгоритм под нативный VP.** Источник данных принципиально другой. Совпадение цифр, достигнутое подкруткой коэффициентов под конкретный инструмент, — это оверфит под чужую реализацию, а не точность. Правильный путь к сходимости один: **улучшать источник данных** (L2 LTF → L3 footprint в P7), а не косметику.

Критерий приёмки поэтому сформулирован честно: **POC в пределах 1 бина, VAH/VAL в пределах 2 бинов на 5m–1H.** Если отклонение больше — это баг, разбираем. Если меньше — хорошо, но специально к нулю не стремимся.

## Обнаруженные ограничения

1. **`for i = 0 to n-1` при `n = 0` в Pine идёт вниз, а не пропускается.** Системная ловушка: пустой массив дал бы обращение по индексу −1 и runtime error. Все циклы обёрнуты в guard'ы. Внесено в правила проекта.
2. **Тернарник не работает с функциями, возвращающими кортеж.** `[a,b] = cond ? f() : g()` пришлось заменить на `if/else`.
3. **`array.sort_indices` заменён на `array.copy` + `array.sort` + порог.** Не из-за ошибки, а чтобы снизить риск компиляции на менее употребимом API. Побочный эффект: при равных объёмах на границе отсечки в Sorted-VA может попасть на 1 бин больше — задокументировано.
4. **Скрытые уровни надо гасить явно.** Линия из пула, которую перестали обновлять, остаётся висеть на старой цене. Исправлено: `putLevel` принимает флаг `show` и прячет линию.
5. **Офлайн-компилятора Pine по-прежнему нет** — критерии B1/B2 подтверждаете вы.

## Следующий этап — P3: VWAP Engine

По roadmap следующим идёт VWAP (P3): он полностью независим от профиля, даёт второй активный компонент scoring и имеет **самый строгий критерий приёмки во всём проекте** — session VWAP обязан побитово совпасть со встроенным `ta.vwap`.

Содержание: session/weekly/monthly, до 3 anchored VWAP со всеми режимами якоря, σ-полосы через `m2 − vwap²` (а не накопление отклонений от бегущего VWAP — иначе полосы систематически занижены), z-score позиции цены.
