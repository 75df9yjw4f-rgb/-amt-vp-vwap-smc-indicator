## 0. Три уровня данных — и почему их нельзя смешивать

| Уровень | Источник | Что это на самом деле | Доступность |
|---|---|---|---|
| **L3 — REAL FOOTPRINT DATA** | `request.footprint()` | TradingView делит объём на «buy»/«sell» на своей стороне, на данных вплоть до 1 тика. **Классификация по направлению цены подбара, а не по агрессору из bid/ask** | Premium/Ultimate, **только PRO-билд** |
| **L2 — LTF PROXY** | `request.security_lower_tf()` | Мы сами классифицируем каждый подбар по положению его закрытия в собственном диапазоне | любой тариф; глубина intrabar-истории ограничена |
| **L1 — BAR-BASED PROXY** | один OHLCV-бар | распределение по модели M1/M2/M3, знак по направлению или положению закрытия | всегда |

**Терминологическая дисциплина, закреплённая в коде.** Слово «Delta» без квалификатора используется **только** для L3 — и даже там в дашборде и в reason-строке компонента написано `footprint tier (price-direction classified, not bid/ask)`. L2 и L1 везде называются `LTF proxy` и `Bar proxy D1/D2` — в коде, в дашборде, в debug-панели, в документации.

**Что по-прежнему невозможно и не появилось:** дельта по агрессору из стакана. Её в Pine нет ни на одном тарифе. L3 — лучшая доступная классификация, и она всё равно не order flow из книги заявок.

Дашборд всегда показывает **фактически использованный** уровень: строка `ORDER FLOW → TIER` и `PROFILE DATA`. Запрошенный уровень не показывается никогда — показать источник лучше имеющегося было бы ровно тем враньём, ради недопущения которого проект и затевался.

## 1. Audit: Pine v6 / `request.footprint` compatibility

Проверено по официальному Pine Script® User Manual (раздел *Other timeframes and data → `request.footprint()`*).

| Требование платформы | Как выполнено |
|---|---|
| `request.footprint(ticks_per_row, va_percent, imbalance_percent)` | вызывается ровно так, один раз, в глобальной области |
| **Ровно ОДИН footprint-запрос на скрипт** | единственный вызов внутри региона; ни один `request.security()` не зависит от footprint-данных, поэтому второго неявного запроса не возникает |
| `ticks_per_row` — «simple int» | берётся из `input.int`, никогда из series |
| Нет параметра timeframe | запрос всегда на текущем ТФ; агрегацию по сессии делает наш Profile Engine |
| Возвращает `na`, методы не принимают `na` | каждый доступ обёрнут в `if not na(fpBar)` |
| `footprint.rows()` отсортирован по возрастанию цены | индекс `0` трактуется как нижняя строка, `n−1` — верхняя (используется в Unfinished Auction) |
| Лимит 40 запросов (64 Ultimate) | используется **2**: footprint + security_lower_tf |

Задействованные методы: `total_volume` · `buy_volume` · `sell_volume` · `delta` · `rows` · `volume_row.up_price` · `down_price` · `buy_volume` · `sell_volume` · `total_volume` · `has_buy_imbalance` · `has_sell_imbalance`.

### Реализованные понятия

| Понятие | Определение в коде |
|---|---|
| **Buy / Sell Volume** | `footprint.buy_volume()` / `sell_volume()` на баре; `volume_row.*` по строкам |
| **Delta** | `footprint.delta()`; кумулятив за сессию + нормировка `cumΔ / Σ|Δ|` |
| **Volume Imbalance** | флаги `has_buy_imbalance()` / `has_sell_imbalance()`, порог `imbalance_percent` (по умолчанию 300 = втрое) |
| **Imbalance Stack** | самая длинная серия **подряд идущих** строк с дисбалансом в одну сторону; серии короче `fpMinStack` считаются нулём |
| **Unfinished Auction** | крайняя строка бара (верхняя или нижняя) содержит объём **с обеих сторон**. Завершённый аукцион печатает односторонний объём на экстремуме |

**Про Unfinished Auction — честно.** Это **одна из нескольких** формализаций концепции. Выбрана она потому, что объективна и вычислима; более «визуальные» определения — нет. Указано и в коде, и здесь.

## 2. Audit: тарифные ограничения

| Билд | Требование | Что внутри |
|---|---|---|
| `build/ACE.pine` (**STD**) | **любой тариф** | L1 + L2. Ноль упоминаний footprint API в коде |
| `build/ACE-Pro.pine` (**PRO**) | **Premium / Ultimate** | L1 + L2 + L3 |

Дословно из документации: *«Accounts with lower-tier plans **cannot use scripts** that request volume footprint data»*. Это не «функция вернёт na» — скрипт просто не запустится. Поэтому вариант B (два билда) не удобство, а необходимость.

**Разделение теперь проверяется автоматически.** `tools/build.py` вырезает регион и затем валидирует результат, игнорируя комментарии и строковые литералы:

```
STD: request.footprint = 0, volume_row = 0, объявлений типа footprint = 0
PRO: request.footprint = 1, volume_row = 6
оба: barmerge.lookahead = 0, varip = 0
```

Если из STD-билда когда-нибудь «просочится» footprint — сборка упадёт. Если PRO-билд потеряет свой вызов — тоже упадёт.

**L2 доступен на всех тарифах**, но глубина intrabar-истории зависит от тарифа: на старых барах массивы приходят пустыми и мы откатываемся на L1 — автоматически и с указанием фактического уровня.

## 3. Audit: realtime / history behaviour

| Уровень | На истории | В реальном времени | Расхождение |
|---|---|---|---|
| **L1 (bar)** | детерминирован | значения живут внутри бара, фиксируются на закрытии | нет |
| **L2 (LTF)** | доступен только на той глубине, куда достаёт intrabar-история; дальше — откат на L1 | массив подбаров **достраивается** по мере формирования бара | ⚠️ да: внутрибарная картинка отличается от финальной; на старой истории уровень другой |
| **L3 (footprint)** | гранулярность **падает с возрастом бара**: 1 тик → 1 с → 1 мин → 60 мин | самые свежие бары — самые точные | ⚠️ **source drift**: значения закрытых баров могут отличаться после перезагрузки графика |

**Source drift — это третья категория честности проекта** (введена в P3, см. `06-repainting.md`). Это не repaint (скрипт ничего не переписывает) и не lookahead (будущее не читается). Это недетерминированность **поставщика данных**. TradingView сам называет footprint *«repainting by design»*.

Как это обозначено в продукте:
- компонент `Volume` помечается флагом `approx` → в дашборде рядом с именем стоит `~`;
- то же для `Volume Prof.`, когда профиль построен на L3 или L2;
- строка `TIER` в дашборде подсвечена жёлтым, когда уровень не `BAR`;
- debug-панель показывает `delta tier`, `ltf resolution`, `footprint available/unavailable`.

**Ещё одно расхождение, специфичное для TF ≥ 1D:** по документации `footprint.total_volume()` может существенно отличаться от переменной `volume`, потому что EOD-фиды включают блочные и OTC-сделки, а интрадей-фиды нет. Поэтому footprint-объём и `volume` нигде не смешиваются в одной формуле.

## 4. Audit: repainting

| Элемент | Repaint | Bar close | Lookahead | Source drift |
|---|---|---|---|---|
| Кумулятивная направленная величина (L1) | ❌ нет | ✅ да | нет | нет |
| Кумулятивная (L2) | ❌ нет | ✅ да | нет | ⚠️ да |
| Кумулятивная (L3) | ❌ нет | ✅ да | нет | ⚠️ да |
| Профиль на L2 / L3 | ❌ нет | ✅ да | нет | ⚠️ да |
| Buy / Sell volume, Delta (L3) | ❌ нет | ✅ да | нет | ⚠️ да |
| Volume imbalances, stacks | ❌ нет | ✅ да | нет | ⚠️ да |
| Unfinished auction | ❌ нет | ✅ да | нет | ⚠️ да |
| RVOL | ❌ нет | ✅ да | нет | нет |

## 5. Audit: performance

### Стоимость на бар

| Операция | Стоимость | При дефолтах |
|---|---|---|
| `request.footprint` (PRO) | 1 запрос | из лимита 40 |
| `request.security_lower_tf` | 1 запрос | из лимита 40 |
| Обход строк footprint (профиль) | `O(rows)` | ~10–40 строк |
| Обход строк footprint (imbalance + stacks) | `O(rows)` | тот же порядок |
| Цикл по подбарам L2 (дельта) | `O(intrabars)` | ≤ `maxIntrabars` = 60 |
| Цикл по подбарам L2 (профиль) | `O(intrabars × бинов на подбар)` | ≤ 60 × ~3 |
| Кумулятивы, RVOL, дивергенция | `O(1)` | — |
| **Добавлено в P7** | | **≈ 250–350 операций/бар** |

### Главный риск и как он закрыт

Дневной график с 1-минутным LTF — это **1440 итераций на бар**, гарантированный `Loop takes too long`.

Закрыто предохранителем `maxIntrabars` (по умолчанию 60) и функцией `ltfPick()`, которая выбирает **самый мелкий ТФ, укладывающийся в бюджет**, из лестницы 1/3/5/15/30/60/240 минут. На дневном графике с бюджетом 60 автоматически выбирается 30 мин (48 подбаров), а не 1 мин.

Если подходящего младшего ТФ нет вообще (например, минутный график), `ltfPick` возвращает пустую строку, LTF-путь выключается, и запрос делается с `ignore_invalid_timeframe = true` — то есть возвращает пустые массивы вместо runtime-ошибки.

Второй предохранитель, унаследованный из P1: `maxBinsPerBar`. Подбар, покрывающий слишком много бинов, откатывается на close-only и помечает профиль `CLAMPED`.

### Бюджеты

| Ресурс | Использовано | Лимит |
|---|---|---|
| `request.*()` | **2** | 40 (64 Ultimate) |
| Boxes / Lines / Labels | без изменений с P6: 75 / 61 / 82 при дефолтах | 500 каждого |
| Plots | 18 | 64 |
| Массивы | профиль ≤ 4×500 + зоны + уровни + LTF-массивы | ~100 000 элементов |

## 9. Known Limitations

1. **L3 — не bid/ask агрессор.** Главное ограничение всего проекта, и оно не изменилось. TradingView классифицирует объём по направлению цены подбара. Это лучшая доступная классификация, но не order flow из стакана. Написано в коде, в дашборде и здесь.
2. **PRO-билд недоступен ниже Premium.** Не деградирует — просто не запускается. Ровно поэтому существуют два билда.
3. **Один footprint-запрос на скрипт.** `ticks_per_row` — глобальный параметр; нельзя иметь грубый footprint для сессии и точный для текущего бара.
4. **Source drift.** Значения закрытых баров на L2/L3 могут отличаться после перезагрузки. Не скрывается: `~`, жёлтый `TIER`, строки в debug.
5. **Гибридная история.** Свежие бары точнее старых. Профиль за длинный период может быть собран из разных уровней. `Profile.model` отражает уровень **текущего** бара, а не всего профиля — это упрощение.
6. **LTF-путь ограничен `maxIntrabars`.** На дневках выбирается 30 мин, а не 1 мин: сознательный размен точности на возможность вообще досчитать.
7. **Unfinished Auction — одна из формализаций.** Выбрана объективная и вычислимая.
8. **Стек дисбалансов влияет на score только при активном L3.** На L1/L2 этих данных просто нет, и компонент их не изобретает.
9. **Order Block по-прежнему не реализован** (не входил ни в P6, ни в P7). Input помечен как inert.
10. **Офлайн-компиляции Pine не существует** — F1/F2 подтверждаете вы. Без изменений с P0.
