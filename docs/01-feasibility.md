## 1.1. Что Pine Script физически НЕ даёт

Это фундамент всего остального аудита. Pine — это язык, исполняющийся **по одному бару за проход**, поверх агрегированных OHLCV-данных. Из этого следует список отсутствующих данных:

| Данные | Доступность | Последствия |
|---|---|---|
| Тиковый поток (каждая сделка) | ⚠️ **косвенно, через `request.footprint()`** (Premium+) | VP высокой точности возможен — см. `08-footprint.md` |
| Стакан / DOM / Level 2 | ❌ нет | Нельзя увидеть лимитные заявки, айсберги, absorption |
| Bid/Ask по каждой сделке | ❌ нет | **Без изменений.** Footprint-дельта классифицирует объём по направлению цены, а не по агрессору |
| Footprint / Cluster | ✅ **есть: `request.footprint()`** (Premium/Ultimate) | строки, buy/sell, delta, imbalances. Time&Sales — по-прежнему нет |
| Open Interest | ⚠️ только через отдельные тикеры (например `BTCUSDT_OI` на некоторых биржах) | Частично, не универсально |
| Объём на споте FX, индексах, части CFD | ❌ часто отсутствует или это tick-count | VP/VWAP деградируют; нужен fallback |
| Исторические intrabar-данные на большую глубину | ⚠️ ограничено тарифом | LTF-режим работает только на недавней истории |

**Ключевой вывод:** всё, что в профессиональных платформах (Sierra Chart, ATAS, Bookmap) строится на тиках и стакане, в Pine либо аппроксимируется, либо не делается вовсе. Любой Pine-индикатор, который заявляет «настоящий footprint / real delta / order flow», — либо использует LTF-аппроксимацию (и должен об этом сказать), либо врёт.

## 1.2. Технические лимиты Pine Script (v6)

Цифры ниже — то, вокруг чего придётся проектировать архитектуру. Часть лимитов зависит от тарифа TradingView, поэтому проектируем «под худший случай» (Basic/Free) с деградацией функций вверх по тарифам.

### Историческая глубина
- Количество баров на графике: **зависит от тарифа** (примерно 5k…25k+ для старших планов). Индикатор не должен ломаться, если истории мало.
- `max_bars_back` — по умолчанию Pine определяет буфер истории автоматически; при динамических обращениях к прошлому (`close[n]`, где n — переменная) нужно указывать явно. Максимум **5000**. Это жёсткий потолок: «профиль за последние 20 000 баров через прямой доступ к прошлому» — невозможен. Решение — инкрементальные накопители (см. §1.6), а не обратный просмотр истории.

### Массивы и память
- Суммарный лимит элементов во всех массивах скрипта: **~100 000**.
- Практический бюджет: 200 бинов × 2 профиля (текущий + предыдущий) = 400 элементов на «объём», плюс параллельные массивы (цена бина, up-vol, down-vol, TPO-count) ×4 = ~1600. Запас огромный. Проблема будет не в памяти, а в **времени исполнения**.

### Графические объекты
- `max_boxes_count` / `max_lines_count` / `max_labels_count`: **до 500 каждого** (по умолчанию 50).
- `max_polylines_count`: **до 100**, но одна polyline вмещает до ~10 000 точек.
- `plot()`: не более **64** штук на скрипт.
- Таблицы (`table`): практически не конкурируют за лимиты боксов/линий — идеальны для дашборда.

**Следствие для VP:** отрисовка профиля боксами (1 бокс = 1 бин) при 200 бинах × 3 профиля = 600 боксов → **выход за лимит**. Значит:
- Standard-режим: боксы, но ≤150 бинов и ≤2 профиля;
- Pro-режим: рендер профиля **одной polyline** (ступенчатый контур гистограммы) — 1 объект вместо 200.

### Исполнение
- Ограничение на время одного цикла: **«Loop takes too long» (~500 мс)**. Вложенный цикл `бары × бины` на каждом баре = гарантированная смерть скрипта.
- Общий лимит времени компиляции/исполнения скрипта (~20–40 с на весь прогон истории). На тяжёлой истории полный пересчёт VP на каждом баре в него не укладывается.
- Лимит `request.*()` вызовов: **40** уникальных на скрипт. Нам нужно 1–4 — не проблема.

### Реальное время
- На незакрытом баре скрипт пересчитывается на каждом тике (`calc_on_every_tick` для индикаторов фактически включён). Значения «живут» внутри бара и фиксируются на закрытии.
- `varip` — переменные, не откатывающиеся между тиками. Нужны для внутрибарной статистики, но делают скрипт **непроверяемым на истории** (на истории `varip` ведёт себя как обычная `var`). Используем минимально и с явной пометкой.

## 1.3. Volume Profile — что реально можно построить

### Чем наш VP будет отличаться от «нативного»

Нативный Volume Profile TradingView строится на **тиковых данных на серверной стороне** (или на данных минимально доступного разрешения). Pine такого доступа не имеет. Поэтому наш VP — это **модель распределения барного объёма по цене**. Доступны четыре модели, от грубой к точной:

| Модель | Как работает | Точность | Цена |
|---|---|---|---|
| **M1 — Close only** | весь объём бара в бин закрытия | очень низкая | O(1) на бар |
| **M2 — Uniform range spread** | объём равномерно по бинам, перекрытым `[low, high]`, пропорционально доле перекрытия бина | средняя | O(bins_in_bar) |
| **M3 — OHLC-weighted** | треугольное/трапециевидное взвешивание с пиком у `hlc3`/`close`, хвостами к `high`/`low` | средняя+ | O(bins_in_bar) |
| **M4 — LTF intrabar** | `request.security_lower_tf()` возвращает массив OHLCV младшего ТФ; к каждому intrabar применяется M2 | **высокая, близко к нативному** | O(intrabars × bins_in_intrabar) |

**Честная оценка M4:** при 5-минутном графике и LTF=1m это 5 подбаров на бар — уже заметно точнее. При дневном графике и LTF=5m это 288 подбаров на бар — точность близка к нативной, но глубина истории LTF ограничена тарифом, и старые бары придётся считать по M2/M3. Это **гибридный профиль**, и дашборд должен показывать, какая модель фактически применена к текущему профилю.

Ограничения `request.security_lower_tf()`:
- глубина доступной intrabar-истории ограничена (зависит от тарифа; на старых барах массив приходит пустым → обязателен fallback);
- в реальном времени массив подбаров **достраивается по мере формирования бара** → картинка внутри текущего бара отличается от финальной (это не repaint прошлого, но это расхождение live/history);
- нельзя запросить ТФ старше текущего.

### Что реализуется полноценно (при выбранной модели распределения)
- бины произвольного количества (input, 10–500);
- POC = бин с максимальным объёмом (с детерминированным правилом разрешения ничьей);
- Value Area по классическому алгоритму расширения от POC парами бинов;
- VAH / VAL;
- HVN / LVN;
- сессионный профиль, профиль за период (день/неделя/месяц), профиль за фиксированный lookback, композитный профиль;
- предыдущий профиль (N предыдущих);
- **developing POC / VAH / VAL** — но с оговоркой по производительности (см. §1.6);
- настраиваемый Value Area % (по умолчанию 70).

### Дополнительно: TPO / Market Profile
Поскольку Market Profile по Стайделмайеру считает **время на цене**, а не объём, его можно построить **без данных об объёме вообще** — просто считая, сколько баров касалось каждого бина. Это:
- работает на инструментах без объёма (спот FX, индексы);
- методологически точнее для AMT, чем volume-профиль;
- по стоимости идентично M2.

Чего не будет: буквенной TPO-разметки (A, B, C…) — рисовать сотни лейблов в сетке нереально в рамках лимита 500 лейблов. Будет «TPO-count гистограмма» + IB + single prints (аналог LVN).

## 1.4. AMT — что поддаётся алгоритмизации

Auction Market Theory — это **интерпретационная рамка**, а не набор формул. Честная позиция: алгоритмизируется не «теория», а её измеримые прокси. Ниже — что именно.

| Понятие AMT | Формализуемо? | Комментарий |
|---|---|---|
| Value Area / POC / VAH / VAL | 🟢 да | чистая арифметика на профиле |
| Initial Balance (IB) | 🟢 да | диапазон первых N минут сессии — объективно |
| Opening Range (OR) | 🟢 да | то же самое, другой период |
| IB extension (1×, 2×) | 🟢 да | арифметика |
| Open type (Open-Drive / Open-Test-Drive / Open-Rejection-Reverse / Open-Auction) | 🟡 частично | классификация по поведению первых баров — правила формализуемы, но **конвенциональны** (несколько разных школ) |
| Balance / Баланс | 🟡 частично | нет единого определения; предложу 3 формализации (§3) |
| Balance → Imbalance переход | 🟡 частично | производная от определения баланса |
| Acceptance | 🟡 частично | «принятие цены» = время + закрытия + миграция стоимости; пороги субъективны |
| Rejection | 🟡 частично | формализуется через возврат в диапазон + хвост |
| Initiative vs Responsive activity | 🟡 частично | классическое определение Далтона (относительно предыдущей Value Area) формализуемо, **но требует направления сделок**, которое мы имеем только как прокси |
| Накопление / Распределение | 🔴 → 🟡 | это интерпретация, а не факт. Максимум — «зона-кандидат»: баланс + HVN + смещение прокси-дельты. Обязана быть помечена как гипотеза |
| «Рынок ищет ликвидность / аукцион движется к справедливой цене» | 🔴 | нарратив, не алгоритм. Не реализуем и не должны |

## 1.5. SMC — что формализуемо объективно

Разделение, о котором вы просили, — **FACT (детекция) vs INTERPRETATION (оценка)** — проводится здесь жёстко.

### FACT — строго детерминированные события
| Элемент | Определение однозначно? | Примечание |
|---|---|---|
| Swing High / Low (pivot) | 🟢 да | `ta.pivothigh(n, n)` — подтверждается через n баров |
| HH / HL / LH / LL | 🟢 да | сравнение подтверждённых свингов |
| BOS | 🟢 да | закрытие/прокол за последним подтверждённым свингом по тренду |
| CHoCH / MSS | 🟢 да | первый пробой в противоположную сторону; MSS = CHoCH + displacement |
| FVG (3-барный гэп) | 🟢 да | `low[0] > high[2]` / `high[0] < low[2]` — абсолютно объективно |
| Equal Highs / Lows | 🟢 да (с допуском) | \|h1−h2\| ≤ tol×ATR; tol — input |
| Sweep / Liquidity grab | 🟢 да | прокол уровня + закрытие обратно; опционально + подтверждение |
| Premium / Discount | 🟢 да | 50% текущего dealing range |
| Displacement | 🟢 да (с порогом) | тело ≥ k×ATR (+ объём, + создаёт FVG) |
| Liquidity levels (equal H/L, day/week H/L, IB H/L) | 🟢 да | объективные ценовые уровни |

### INTERPRETATION — конвенциональные, требуют выбора формализации
| Элемент | Проблема | Решение |
|---|---|---|
| **Order Block** | 5+ конкурирующих определений (последняя противоположная свеча / свеча с макс. объёмом / зона консолидации / body vs wick границы) | реализуем как **выбираемый профиль правил** (input: `OB Rule = Last Opposite Candle / Highest Volume Candle / Body-Threshold`), с явной пометкой «convention-dependent» |
| **Breaker / Mitigation Block** | производные от OB, наследуют его неоднозначность | Phase 2, по желанию |
| «Сильный / слабый» BOS | оценочное суждение | **не выводим как факт** — уходит в score как взвешенный вклад |
| «Институциональный / smart money» | маркетинговый нарратив | **не используем вообще** |
| Inducement / Liquidity engineering | сильно субъективно | не входит в v1.0 |

### Direction / Delta proxy
Настоящей дельты нет. Прокси-варианты, от худшего к лучшему:
1. `close > open ? +vol : -vol` — грубо, но детерминированно;
2. взвешивание по позиции закрытия в диапазоне: `vol × (2×(close−low)/(high−low) − 1)`;
3. **LTF-агрегация**: через `request.security_lower_tf()` классифицировать каждый подбар по п.1/п.2 и суммировать — это то, что TradingView делает в своём «Up/Down Volume».

Всё это — **аппроксимация agressor-flow, а не дельта**. В дашборде будет подписано как `Δ proxy`, не как `Delta`.

## 1.6. Производительность — главный технический риск

Наивная реализация убивает скрипт. Разберём где именно.

**Проблема 1: пересчёт профиля на каждом баре.**
Профиль за lookback L баров с B бинами при полном пересчёте на каждом баре стоит O(L×B) за бар и O(N×L×B) на всей истории. При L=500, B=100, N=10000 это 5×10⁸ операций — скрипт не скомпилируется/отвалится по таймауту.

**Решения (все применяются):**
- **Add-only профили.** Сессионные/периодные профили не требуют вычитания: на каждом баре добавляем вклад одного бара в накопитель → **O(bins_in_bar) ≈ O(1..5) за бар**. Это делает developing POC/VA дешёвыми.
- **Rolling lookback профиль** (скользящее окно) требует вычитания выбывающего бара → надо хранить вклад каждого бара. Дорого по памяти. **Рекомендация: rolling-VP считать только на последнем баре** (`barstate.islast`) — это стандартная практика и визуально ничего не теряет (историческая гистограмма всё равно не видна).
- **Декимация developing-линий:** пересчёт POC/VA не чаще, чем раз в K баров (input, по умолчанию 1 для Pro, 5 для Standard, off для Lite).
- **Фиксированная сетка бинов.** Если границы профиля меняются при каждом новом экстремуме, весь накопитель приходится перестраивать. Решение: сетка бинов фиксируется на старте сессии/периода с запасом (например ±ATR×k), либо применяется «rebin» с усечением — но это событие редкое, а не поканальное.
- **Value Area:** алгоритм расширения от POC — это один проход ≤ B итераций, O(B) на пересчёт. Приемлемо.
- **Рендер:** polyline вместо 200 боксов; `label`/`box` пересоздаются только при изменении значения, а не каждый бар.

**Проблема 2: LTF (`request.security_lower_tf`).** Самая дорогая часть. При дневном графике и LTF=1m — 1440 элементов массива на бар, и цикл по ним на каждом баре. Это **гарантированный timeout**. Ограничения:
- LTF-режим доступен только в Pro-режиме;
- жёсткий guard: соотношение TF/LTF не больше ~N подбаров (input, по умолчанию 60); иначе авто-подбор LTF;
- LTF применяется только к текущему и предыдущему профилю, не ко всей истории.

**Проблема 3: массивы объектов SMC.** Массивы FVG/OB/liquidity должны иметь **жёсткий cap** (input, например max 30 активных) с вытеснением старейших, иначе упрёмся в лимит боксов и в стоимость обхода массива на каждом баре.

## 1.7. Repainting — предварительная оценка (детально — в отдельном документе)

| Категория | Статус |
|---|---|
| VWAP, Anchored VWAP, полосы | ✅ no repaint (значение внутри текущего бара живое, на закрытии фиксируется) |
| Профиль, POC, VAH, VAL, HVN/LVN | ✅ no repaint на закрытых барах; developing-значения обновляются внутри бара |
| Swing / pivot | ⚠️ **не repaint, но lag**: свинг подтверждается через n баров. Исторически он виден «сразу», в реальном времени — с задержкой n баров. Это главная причина, по которой pivot-индикаторы выглядят на истории лучше, чем работают live. Будет явно указано и опционально визуализировано |
| BOS / CHoCH / MSS | ✅ no repaint при подтверждении на закрытии бара; наследуют lag свингов |
| FVG | ✅ no repaint (подтверждается на закрытии 3-го бара) |
| Sweep | ✅ no repaint при `close`-подтверждении; ⚠️ при внутрибарном режиме — мигает до закрытия |
| Order Block | ✅ no repaint по факту, но **зона задним числом**: OB маркируется только после displacement/BOS, т.е. рисуется на свече в прошлом. Это не repaint, но создаёт иллюзию раннего сигнала |
| LTF-данные | ⚠️ live ≠ history: внутри формирующегося бара массив подбаров неполон; на старой истории LTF-данных нет вообще |
| Score / Context | ✅ no repaint при `Confirm on bar close = true` (по умолчанию ON) |
| `barmerge.lookahead_on` | ❌ **не используем нигде** |

## 1.8. ИТОГОВЫЙ VERDICT

### 🟢 FULLY POSSIBLE
Реализуемо полноценно и объективно:
- **VWAP**: сессионный, дневной, недельный, месячный, якорный (произвольная дата, свинг, BOS, экстремум), полосы σ (1/2/3), z-score позиции цены.
- **Профильная арифметика**: бины, POC, Value Area (классический алгоритм), VAH/VAL, HVN/LVN, developing POC/VA, предыдущие профили, композитный профиль, настраиваемый VA%.
- **TPO / time-at-price профиль** (работает даже без объёма).
- **Initial Balance, Opening Range, IB-расширения.**
- **Market Structure**: swings, HH/HL/LH/LL, BOS, CHoCH, MSS.
- **FVG** (детекция + степень митигации).
- **Equal Highs/Lows, пулы ликвидности, sweep/liquidity grab.**
- **Displacement** (по заданному порогу).
- **Premium/Discount/EQ** от dealing range.
- **Relative Volume (RVOL)** как подтверждение.
- **Scoring engine + Context Dashboard** с полной расшифровкой вкладов.
- Режимы Lite / Standard / Pro.

### 🟡 PARTIALLY POSSIBLE
Реализуемо, но это **модель/аппроксимация**, и пользователь обязан это видеть:
- **Volume Profile как таковой** — распределение барного объёма по модели M1–M4, не по тикам. Совпадение с нативным VP — высокое по форме, но не побитовое. LTF-режим приближает, но ограничен глубиной истории.
- **Delta / направленный объём** — только прокси (по закрытию, по позиции закрытия в диапазоне, либо LTF-агрегация). Подписывается как `Δ proxy`.
- **Balance / Imbalance** — нет канонического определения; даём 3 формализации на выбор (range/ATR, Value-Area overlap, Efficiency Ratio) + комбинированный режим.
- **Acceptance / Rejection** — формализуемо, но пороги (сколько закрытий, сколько времени) конвенциональны и вынесены в inputs.
- **Initiative / Responsive activity** — классическое определение Далтона реализуемо относительно предыдущей Value Area, но опирается на прокси-направление.
- **Order Block** — несколько конкурирующих конвенций; даём выбор правила, честно маркируем как convention-dependent.
- **Open type классификация** — правила формализуемы, школы расходятся.
- **Зоны накопления/распределения** — только как «кандидаты» с явной пометкой INTERPRETATION.
- **Исторические профили на глубокой истории** — ограничены `max_bars_back` и бюджетом исполнения; глубина конфигурируема.

### 🔴 NOT POSSIBLE
Не делаем, потому что данных нет или это не алгоритм:
- Настоящий тиковый Volume Profile, footprint, cluster-чарт.
- Настоящая Delta / agressor-классификация сделок.
- Стакан, absorption, айсберги, spoofing, любые DOM-производные.
- Cumulative Volume Delta как точная величина (только прокси).
- Буквенная TPO-разметка (A/B/C…) в полном виде.
- Определение «кто именно покупал» — институционал / ритейл / маркет-мейкер. Такой информации в данных нет ни в каком виде.
- «Предсказание» направления, вероятности, «точность 90%», «умные деньги знают».
- Полная межтаймфреймовая репликация нативного VP TradingView.
- Мультисимвольный анализ ликвидности в реальном времени без ограничений `request.security`.
