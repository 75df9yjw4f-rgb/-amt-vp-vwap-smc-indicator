# Этапы 8, 10, 11 — Производительность, название, план разработки

## Этап 8 — Бюджет производительности

### Стоимость на бар (Standard, 50 бинов)

| Операция | Стоимость/бар | Комментарий |
|---|---|---|
| Вклад бара в add-only профиль (M3) | O(бинов, пересечённых баром) ≈ 1–8 | основной путь |
| Пересчёт POC | O(bins) = 50 | можно декимировать |
| Пересчёт Value Area | O(bins) = ≤50 | декимируется вместе с POC |
| VWAP + 3 полосы × 4 якоря | O(1) | накопители, дёшево |
| Свинги, BOS, CHoCH | O(1) | встроенные `ta.pivot*` |
| Обход массива зон (FVG/OB/liq) | O(maxZones) = 25 | cap обязателен |
| Scoring | O(7) | пренебрежимо |
| Дашборд | только `barstate.islast` | не влияет на прогон |
| **Итого** | **~150 операций/бар** | укладывается с запасом |

### Где всё ломается и как это предотвращено

| Риск | Симптом | Решение в архитектуре |
|---|---|---|
| Полный пересчёт профиля на каждом баре | таймаут компиляции | add-only накопители; rolling-VP только на `barstate.islast` |
| LTF на большом отношении TF/LTF | «Loop takes too long» | guard `maxIntrabars` (default 60) + авто-подбор LTF + доступно только в Pro |
| Рост числа зон без ограничения | превышение лимита боксов, замедление | жёсткий `maxZones` + `box.delete` при вытеснении |
| 200 бинов × 3 профиля боксами | 600 > 500 лимит | polyline-рендер в Pro; ограничение бинов в Standard |
| Пересоздание объектов каждый бар | утечка и лимиты | создание один раз + `set_*` |
| Динамический `close[n]` | ошибка `max_bars_back` | явный `max_bars_back = 5000` + отказ от динамического обратного доступа в пользу накопителей |
| `rebin` при каждом новом экстремуме | O(bins) слишком часто | запас сетки ±3·ATR на старте периода |
| Лейблы на всей истории | лимит 500 | `maxDrawBars` — рисуем только последние N баров |

### Режимы
`Lite` / `Standard` / `Pro` — параметры в `docs/03-architecture.md §3.5`. Режим задаёт дефолты; любой отдельный переключатель их перекрывает.

## Этап 10 — Варианты названия

Требование: отражать объединение AMT + Volume Profile + VWAP + Market Structure, без маркетингового шума и без чужих брендов.

| # | Название | Логика |
|---|---|---|
| 1 | **Auction Context Engine (ACE)** | точно описывает суть: движок рыночного контекста на базе аукциона. Аббревиатура запоминается |
| 2 | **Market Auction Framework — AMT · VP · VWAP · Structure** | максимально прямолинейно и честно, описание в названии |
| 3 | **Value & Structure** | два столпа: стоимость (VP/VWAP/AMT) и структура (SMC). Лаконично |
| 4 | **Auction Flow Context** | ваш вариант «Auction Flow» + акцент на контекст, а не на сигналы |
| 5 | **Fair Value Framework** | VWAP и Value Area — обе про справедливую цену; FVG вписывается |
| 6 | **Auction Map** | профиль + структура как карта аукциона, не как предсказание |
| 7 | **Context: Auction & Structure (CAS)** | слово «Context» первым — сразу задаёт ожидания |

**Рекомендация: `Auction Context Engine (ACE)`** — одновременно описывает архитектуру (движок контекста), позиционирует как decision-support, а не сигнальный, и не пересекается с известными брендами. Полное имя для публикации: `Auction Context Engine — AMT · Volume Profile · VWAP · Market Structure`.

## Этап 11 — Roadmap разработки

Каждая фаза — отдельный рабочий Pine-скрипт, который компилируется и проверяется на графике. Никаких «напишем 3000 строк и потом отладим».

| Фаза | Содержание | Критерий готовности |
|---|---|---|
| **P0. Каркас** | `indicator()` с лимитами, все группы inputs, UDT, режимы, тема, пустой дашборд, guard'ы (`volumeValid`, `maxIntrabars`) | компилируется, дашборд рисуется, inputs не ломают друг друга |
| **P1. Profile Engine** | сетка бинов, модели M1–M3, add-only накопление, POC, VA (оба алгоритма), VAH/VAL, рендер боксами | POC/VA визуально совпадают с нативным VP TradingView в пределах ширины бина |
| **P2. Профили и узлы** | предыдущие профили, developing POC/VA с декимацией, HVN/LVN, TPO-режим, polyline-рендер | работает на инструменте без объёма (TPO fallback) |
| **P3. VWAP Engine** | session/week/month, 3× anchored, все режимы якоря, σ-полосы по `m2 − vwap²`, z-score | session VWAP совпадает со встроенным `ta.vwap` побитово |
| **P4. AMT Layer** | IB/OR + расширения, balance B1–B4, переход баланс→дисбаланс, acceptance, rejection, initiative/responsive | ручная проверка на 3 инструментах × 2 ТФ |
| **P5. Structure Engine** | свинги, HH/HL/LH/LL, trend-state, BOS, CHoCH, MSS, dealing range, premium/discount | нет «двойных» BOS, состояние не залипает |
| **P6. Liquidity & Imbalance** | EQH/EQL, пулы, sweep (оба режима), FVG + митигация, displacement, OB (3 правила) | лимиты объектов не превышаются на 20k баров |
| **P7. LTF-модель M4** | `request.security_lower_tf`, D3, авто-подбор LTF, fallback, индикация модели в дашборде | нет таймаутов на D/W ТФ; fallback срабатывает корректно |
| **P8. Context Engine + Scoring** | 7 компонентов, непрерывные `s`, веса, затухание, bias/bull/bear/confidence, `WHAT CHANGED` | bias инвариантен к отключению компонентов |
| **P9. Dashboard + Alerts** | полная таблица, секции LEVELS и DATA, `alertcondition` только по FACT-событиям | все числа в таблице проверяемы вручную |
| **P10. Repaint-аудит** | процедура из `docs/06-repainting.md`, отчёт | `docs/REPAINT-TEST-REPORT.md` опубликован |
| **P11. Оптимизация** | профилирование, финальная настройка Lite/Standard/Pro | Pro не таймаутится на 20k баров; Lite работает на слабом железе |
| **P12. Документация и релиз** | описание для TradingView, тултипы, MPL-2.0, честные дисклеймеры | нет ни одного маркетингового утверждения |

### Правила, действующие всю разработку
1. Код пишется с нуля; сторонние фрагменты не копируются (`docs/02-licensing.md`).
2. FACT-модули не содержат оценочных суждений — только детекция.
3. Каждый новый порог — input с тултипом, а не магическое число в коде.
4. Каждое конвенциональное определение помечается в UI как convention-dependent.
5. Никаких утверждений о точности, доходности или «умных деньгах».
6. Любой элемент с задержкой/backpainting документируется в тултипе самого параметра.
