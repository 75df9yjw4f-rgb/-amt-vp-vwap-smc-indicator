# 14. Claude как аналитический Decision Engine поверх ACE

**Границы этапа:** только `ACE → DATA → CLAUDE → DECISION → LOG`.
Брокер, биржа, ордера, исполнение, position sizing, уведомления — **вне этапа**.
**ACE v1 не изменён.** Ни одной правки. Всё ниже — исследование.
**Дата:** 2026-09-14.

## 0. ГЛАВНЫЙ ВЫВОД ЭТОГО ЭТАПА

Я проверил по исходному коду каждый пункт вашего списка из 38 позиций. Результат
короткий и неприятный:

> **ACE считает почти всё, что вы перечислили. Наружу выходит около пятой части.**
>
> И упирается это **не в транспорт** (вебхук / CSV / алерт — не важно), а в то, что
> значение, которое скрипт не плотит, не покидает скрипт **никаким** способом.

Прямое следствие для вашей задачи: **тот уровень анализа, который вы описали в §3
вашего задания, на неизменённом ACE недостижим.** Не «неудобен» — недостижим.
Entry/Stop/Target строятся на уровнях (свинг, FVG, свип, статический VAH), а наружу
выходит факт «BOS произошёл» без цены, на которой он произошёл.

Но есть хорошая новость, и она структурирует весь план:

> **Нулевого изменения ACE достаточно, чтобы построить baseline A, B и харнесс.
> Его недостаточно, чтобы проверить гипотезу D (ценность Claude).**

Поэтому правильный порядок — начать без правок, упереться в стену осознанно, и только
тогда принимать решение о минимальной аддитивной правке. Заморозка scope держится
настолько долго, насколько это вообще возможно.

## 2. МИНИМАЛЬНАЯ ПРАВКА ACE — ЕСЛИ ВЫ НА НЕЁ ПОЙДЁТЕ

Я **не** вношу её. Описываю, чтобы решение было вашим и информированным.

### 2.1 Что именно потребовалось бы

Блок `plot(..., display = display.data_window)` в конец файла. Свойства:

- **ноль изменений в расчётах.** Ни один движок, ни одна формула, ни один вес.
- **ноль изменений в скоринге.** `bias`/`confidence` не трогаются.
- **ноль новых концепций.** Ничего не добавляется — только экспортируется посчитанное.
- визуально ничего не меняется: `display.data_window` не рисует на графике.
- лимит плотов индикатора — 64; сейчас 18, нужно ~+30. Влезает.

### 2.2 Жёсткое ограничение этого пути

**Плот несёт только число.** Строки (`state`, `reason`, текст WHAT CHANGED) не
экспортируются никогда. Их пришлось бы кодировать целыми числами (enum → int) — то есть
я получу `structure_state = 3`, а расшифровку `3 = bullish HH/HL` мне даст харнесс из
таблицы соответствия.

Это рабочее решение, но это потеря той самой человекочитаемой формулировки, ради которой
дашборд ACE и делался.

### 2.3 Три варианта — честное сравнение

| | Правок ACE | Что даёт | Чего не даёт |
|---|---|---|---|
| **A. Ничего не менять** | 0 | baseline A/B, харнесс, CSV-история | уровни, компоненты, AMT, ликвидность — **тест гипотезы D невозможен** |
| **B. +30 числовых плотов** | аддитивно, логика не тронута | ~95% списка числами | строки/тексты |
| **C. Порт ACE в Python** | 0 (ACE остаётся как есть) | всё, полный контроль, быстрый реплей | недели работы + обязанность доказать паритет с Pine |

**Моя рекомендация:** A сейчас → упереться → B, если решите. C — если проект переживёт
первые измерения и станет долгосрочным.

## 4. LONG / SHORT / HOLD — ФОРМАЛЬНЫЕ ПРАВИЛА

### 4.1 Принцип

Не «Bias > 0 → LONG». Решение принимается по **согласованности слоёв**, и вес имеет
не количество согласных факторов, а **отсутствие противоречащих**.

Четыре слоя, каждый даёт `+1 / 0 / −1 / n/a`:

| Слой | Бычий | Медвежий |
|---|---|---|
| **Location** (где цена) | в discount, у поддержки, ниже VA | в premium, у сопротивления, выше VA |
| **Structure** | HH/HL, bullish BOS | LH/LL, bearish BOS |
| **Auction** (AMT+VP) | acceptance выше reference | acceptance ниже reference |
| **Flow** (VWAP+volume) | VWAP reclaim, объём подтверждает | VWAP loss, объём не подтверждает |

### 4.2 Правила

**LONG** — требуется всё:
1. ≥3 слоя бычьи, **ни один явно медвежий**;
2. ACE Bias > 0 **или** Bias ≈ 0 при явном локальном перевесе (расхождение объясняется в `conflicts`);
3. есть **конкретный уровень стопа** — не «примерно ниже»;
4. планируемый R:R ≥ 1.5 до ближайшего логичного таргета;
5. цена **не в середине диапазона** без края поблизости.

**SHORT** — зеркально.

**HOLD / NO TRADE** — во всех остальных случаях. Это **исход по умолчанию**, а не
«ничего не нашлось».

### 4.3 Обязательный HOLD — таксономия

Ниже не «рекомендации», а случаи, когда HOLD **обязателен**:

| Код | Ситуация |
|---|---|
| `CONFLICT` | слои противоречат (ваш пример: bias bullish + ликвидность сверху снята + AMT rejection) |
| `NO_LEVEL` | нет уровня для стопа → нет сделки. Без исключений |
| `MID_RANGE` | цена в середине баланса, край далеко, R:R плохой по построению |
| `LOW_COVERAGE` | компоненты INVALID, работает меньшинство — **NO DATA ≠ NEUTRAL** |
| `STALE` | снимок устарел / пропуск баров |
| `POST_MOVE` | движение уже произошло, вход опоздал (расстояние до стопа больше нормы) |
| `EVENT_UNCONFIRMED` | событие есть, подтверждения нет (pivot lag) |
| `REGIME_MISMATCH` | сетап требует тренда, рынок в балансе (или наоборот) |
| `COOLDOWN` | недавняя инвалидация по тому же уровню |
| `MISSING_DATA` | нужного факта нет в снимке (пока ACE не изменён — частый случай) |

**Ожидаемая доля HOLD — 70–90%.** Если она систематически ниже — это признак, что я
подгоняю обоснование под желание торговать, и это само по себе метрика (§10).

## 5. ENTRY / SL / TP — ЧЕСТНО О ДОСТАТОЧНОСТИ ДАННЫХ

### 5.1 На неизменённом ACE

| Параметр | Данных достаточно? | Комментарий |
|---|---|---|
| **Entry** | 🟡 частично | есть developing VA и VWAP → отталкиваться можно. Нет FVG, свипов, свингов — то есть **лучших** точек входа |
| **Stop** | ❌ **нет** | нет цен свингов, нет границ зон, нет ATR. Стоп не на чем построить |
| **Take Profit** | 🟡 частично | есть developing VA и полосы VWAP. Нет статического VAH/VAL, нет уровней ликвидности |
| **Invalidation** | 🟡 частично | цена — да; события BOS/CHoCH — да (сам факт); уровневые — нет |
| **Trailing / management** | ❌ нет | требует структуры и уровней |

**Вывод без обиняков: на неизменённом ACE полноценный торговый план построить нельзя.**
Отсутствие стопа — блокирующее.

### 5.2 Единственное исключение, которое я предлагаю

**ATR считать в харнессе из экспортированного OHLC**, с тем же `atrLen`, что в ACE.
Это не новый рыночный индикатор — ACE его уже считает внутри (`ta.atr`), просто не
экспортирует. Расчёт по OHLC тривиален и точно воспроизводим.

Это снимает блокирующую проблему стопа частично: появляется волатильностный стоп
(`entry ± k·ATR`). Структурный стоп (под свингом) без правки ACE остаётся невозможным.

### 5.3 После аддитивных плотов (вариант B)

Все пять строк становятся ✅. Стоп под свингом, вход от границы FVG, таргет на
статический VAH и на ближайший пул ликвидности, инвалидация по уровню.

## 6. ДИНАМИЧЕСКОЕ РЕШЕНИЕ

### 6.1 Принцип

Решение — не выстрел, а **гипотеза с условиями жизни**. Каждый новый бар: сначала
механическая проверка инвалидации, потом — нужен ли пересмотр вообще.

### 6.2 Три класса изменений

**Класс 1 — ЖЁСТКАЯ ИНВАЛИДАЦИЯ. Меня не спрашивают.**
Проверяется харнессом механически; идея закрывается, даже если я недоступен.

- цена за уровнем стопа
- `CHoCH` против направления идеи
- истёк `time_horizon_bars`
- истёк `valid_for_bars` неисполненного входа

**Класс 2 — ОБЯЗАТЕЛЬНЫЙ ПЕРЕСМОТР. Меня вызывают с полным снимком.**

| Событие | Почему |
|---|---|
| `BOS` / `MSS` | сменилась структура — основание идеи |
| `Sweep` | ликвидность снята; часто разворачивает смысл |
| VWAP reclaim / loss | смена режима потока |
| Acceptance / Rejection у VAH/VAL | суть AMT: принятие или отторжение |
| FVG mitigation > порога | зона-опора перестала быть опорой |
| Переход AMT balance ↔ imbalance | сменился режим — сетап может стать неприменим |
| Смена знака Bias | база контекста |
| `Confidence` упала ниже порога входа | основание ослабло |
| **Компонент сменил VALID ↔ INVALID** | сменился знаменатель скоринга. **Самое неочевидное** — bias двигается без движения компонентов. ACE специально это отмечает в WHAT CHANGED |
| WHAT CHANGED назвал движущим компонент из `facts_used` | изменилось именно то, на чём стояла идея |

**Класс 3 — ИНФОРМАЦИОННЫЕ. В снимок пишутся, пересмотр не запускают.**
Малые колебания bias/confidence ниже `changeMin`; события не по нашим уровням;
изменения компонентов с нулевым весом.

### 6.3 Бюджет пересмотров

Пересматривать каждый бар — дорого и вредно (шум + соблазн «поправить» идею).
Правило: **пересмотр по событию класса 2, плюс принудительно раз в N баров** (N ≈ 12
на 5m). Между пересмотрами живут только механические условия класса 1.

## 7. МАШИНА СОСТОЯНИЙ

### 7.1 Что убрано из вашей схемы и почему

- **TRIGGER** — это событие, не состояние. Переход `SETUP → ACTIVE`.
- **MANAGEMENT** — поведение внутри `ACTIVE`, не отдельное состояние.
- **EXIT** и **INVALIDATED** — разные причины одного исхода; сохраняю оба, но как
  терминальные, потому что различие важно для статистики.

### 7.2 Пять состояний

```
      ┌──────────────────────────────────────────────┐
      ▼                                              │
 ┌──────────┐  условия складываются   ┌─────────┐    │
 │ NO_TRADE │ ──────────────────────► │  SETUP  │    │
 └──────────┘                         └────┬────┘    │
      ▲                                    │         │
      │              триггер: цена достигла│уровня   │
      │                                    ▼         │
      │                              ┌──────────┐    │
      │                              │  ACTIVE  │    │
      │                              └────┬─────┘    │
      │                    ┌──────────────┴───────┐  │
      │                    ▼                      ▼  │
      │            ┌─────────────┐         ┌──────────┐
      │            │ INVALIDATED │         │  EXITED  │
      │            └──────┬──────┘         └────┬─────┘
      │                   └────────┬────────────┘
      │                            ▼
      │                      ┌──────────┐
      └──────────────────────│ COOLDOWN │
                             └──────────┘
```

| Состояние | Смысл | Выход |
|---|---|---|
| `NO_TRADE` | базовое. Большую часть времени система здесь | условия складываются → SETUP |
| `SETUP` | идея сформулирована, вход **не** случился. Есть срок годности | триггер → ACTIVE; протух/сломался → NO_TRADE |
| `ACTIVE` | идея живёт. Внутри — management: перенос стопа, частичная фиксация | стоп/инвалидация → INVALIDATED; таргет/решение → EXITED |
| `INVALIDATED` | гипотеза опровергнута | → COOLDOWN |
| `EXITED` | идея отработала | → COOLDOWN |
| `COOLDOWN` | N баров без новой идеи **в ту же сторону на том же уровне** | → NO_TRADE |

**Зачем COOLDOWN:** без него после инвалидации я с высокой вероятностью немедленно
переоткрою ту же идею с чуть сдвинутым стопом. Это самый типичный способ превратить
один убыток в серию.

## 8. ГДЕ МОЖЕТ БЫТЬ EDGE — И ГДЕ ЕГО НЕТ

### 8.1 Стратегии, естественно следующие из ACE

| # | Подход | Из чего следует | Источник возможного edge | Где обязан проигрывать |
|---|---|---|---|---|
| 1 | **Ротация в балансе** (от края VA к POC) | VP + AMT | переоценка пробоев в боковике | тренд: каждый «край» пробивается |
| 2 | **Acceptance breakout** (баланс → дисбаланс) | AMT acceptance + displacement | смена режима реальна и распознаётся рано | чоп: серия ложных пробоев |
| 3 | **Sweep + CHoCH разворот** | Liquidity + Structure | механика стоп-ранов | свип оказался продолжением |
| 4 | **VWAP reclaim / z-score экстремум** | VWAP + bands | VWAP как бенчмарк исполнения | сильный тренд: цена не возвращается |
| 5 | **Ретест FVG после displacement** | Imbalance + Structure | заполнение дисбаланса | displacement был истощением |

Подходы 1 и 2 **взаимоисключающи по режиму**. Это не недостаток — это значит, что
определение режима является центральной задачей, а не деталью.

### 8.2 Где ACE даёт ложные сигналы (по его же документации)

| Источник | Проявление |
|---|---|
| **Pivot lag** | структура подтверждается через `swingLen` баров → BOS приходит после движения |
| **Developing profile** | POC/VA двигаются внутри периода → ранние уровни ненадёжны |
| **Sweep, immediate режим** | любой хвост за уровень выглядит свипом |
| **Тонкая ликвидность** | бины профиля разрежены, POC прыгает |
| **L1/L2 прокси** | delta — это направленный объём, **не** агрессор. ACE это прямо документирует |
| **Смена слоя L2↔L3** | source drift: смысл цифры меняется без смены самой цифры |

### 8.3 Структурная слабость скоринга — и где именно может жить ценность Claude

Это главное наблюдение раздела.

ACE складывает компоненты **аддитивно с фиксированными весами**. Среди них есть и
трендовые (структура, displacement), и возвратные (положение относительно VA, z-score
VWAP). В сильном тренде они говорят противоположное:

- структура: «продолжение вверх»
- VP/VWAP: «цена перерастянута, далеко от значения»

Сумма → **bias около нуля и низкий agreement именно тогда, когда движение самое чистое.**

Это не баг ACE — это цена честного взвешивания без модели режима. И это **конкретное
место, где интерпретация может добавить то, чего формула не может**: распознать режим и
понять, какой блок компонентов сейчас релевантен, а какой шумит.

Если ценность Claude в этой системе где-то есть, то вероятнее всего **здесь**, а не в
поиске входов.

### 8.4 Режимы

**Должна работать:** инструменты с осмысленным профилем и сессионной структурой —
индексные фьючерсы, ликвидные крипто-мажоры, мажорные FX. Таймфреймы 5m–1h.

**Должна проигрывать:** неликвидное; гэпы и новости (профиль не успевает); очень низкие
ТФ (доминирует микроструктура, а delta — прокси); режимные переломы (все компоненты
запаздывают одновременно).

### 8.5 A / B / C / D

| | Что это | Ожидание | Главная проблема |
|---|---|---|---|
| **A** | `sign(Bias)` | edge ≈ 0 | смешанный осциллятор; нет стопа, нет таргета — это не стратегия |
| **B** | Bias + фильтр Confidence | меньше сделок, возможно лучше на сделку | confidence — согласие модели, **не** вероятность |
| **C** | ACE + механические правила | **первая настоящая стратегия**; есть вход/стоп/цель, воспроизводима, дёшева | режим задан жёстко |
| **D** | ACE + интерпретация Claude | может добавить: распознавание режима, отказ при конфликте, выбор уровня | недетерминизм, стоимость, риск загрязнения (§9) |

**Правильный вопрос — не «D прибыльна?», а «D − C > 0?».** Абсолютный результат D без
сравнения с C не значит ничего.

### 8.6 Где я скорее всего добавляю ценность, а где нет

Честная гипотеза, которую и надо проверять:

> Я вероятнее полезен в том, чтобы **сказать НЕТ**, чем в том, чтобы найти вход.

Отказ от сделки при противоречии слоёв — это суждение, и оно плохо формализуется.
Выбор точки входа — это арифметика по уровням, и её механическое правило делает лучше,
дешевле и одинаково каждый раз.

Отсюда самая дешёвая проверка: **C против C + вето Claude**. Изолирует вклад, не требует
от меня генерации входов, и оценивается на порядок меньшей выборкой.

## 9. КАК ТЕСТИРОВАТЬ БЕЗ HINDSIGHT

### 9.1 Что работает в нашу пользу

P10 уже проверил ACE на repainting и задокументировал четыре категории. Именно это
делает честный бэктест **возможным**: значения плотов в CSV на историческом баре равны
тем, что были в реальном времени, потому что неповторяемость проверена отдельно.
Работа P10 — фундамент этого раздела, а не формальность.

### 9.2 Правила снимка

1. Снимок бара `t` содержит **только** данные с `as_of ≤ t`.
2. Каждый факт несёт `confirmed: true|false`. **Неподтверждённое не может быть
   основанием входа.**
3. Pivot lag учитывается по **времени знания**, не по времени события: свинг на `t−n`
   появляется в снимке `t`, и в снимке помечен `detected_at: t`.
4. Developing-значения помечены `developing: true` и никогда не выдаются как финальные.
5. Смена слоя L1/L2/L3 фиксируется в снимке (source drift виден).
6. Будущих баров в снимке нет физически — харнесс строит его из среза, а не из
   полного массива.

### 9.3 Проблема, специфичная для меня

**Я обучен на данных, включающих исторические рынки.** На известном инструменте и
известной дате я могу «помнить» исход. Промптом это не лечится.

Меры (ослабляют, не устраняют):
- **анонимизация**: убрать тикер, даты, абсолютные цены; подавать нормализованные
  величины (расстояния в ATR, положение в % диапазона);
- период **после даты отсечения обучения**;
- главный вес — **forward/shadow**, а не история;
- исторический прогон считать **проверкой механики харнесса**, а не оценкой edge.

### 9.4 Протокол

1. **Слепой прогон.** Снимок анонимизирован. Исход считает отдельный процесс.
2. **Без обратной связи.** Промпт не меняется в течение прогона. Совсем.
3. **Тест на согласованность.** Тот же снимок дважды → насколько совпали решения.
   Это измеряет мой шум и это самостоятельная метрика.
4. **Аудит `facts_used`.** Ссылка на факт вне снимка → решение помечено и исключено.
5. **Пары.** C и D на **одних и тех же барах**; доверительный интервал считается для
   **разницы** (bootstrap), не для абсолютных результатов.

### 9.5 Размер выборки — без иллюзий

На 30 сделках нельзя отличить ожидание +0.1R от −0.1R. На 100 нельзя надёжно отличить
winrate 50% от 55%. Для небольшого преимущества нужны **сотни** решений.

Это главный способ потерять деньги на автоматизации: принять удачную серию за
подтверждение.


### 10.2 Два правила, без которых лог бесполезен

1. **`snapshot_json` сохраняется целиком и неизменно.** Иначе решение потом не
   воспроизвести и не проверить на lookahead.
2. **Поля исхода пишет отдельный процесс, после.** Они физически не могут попасть в
   снимок следующего решения по той же идее — иначе я «узнаю» результат.

### 10.3 Метрики качества решений (не P&L)

доля HOLD · распределение `no_trade_reason` · доля решений с невалидной схемой ·
доля `HALLUCINATED` (ссылки на отсутствующие факты) · согласованность при повторе ·
частота `facts_missing` по полям — **это прямой количественный ответ на вопрос,
каких данных ACE не хватает** · средний planned R:R против реализованного ·
разбивка по режимам.

## 11. ДИСЦИПЛИНА ПРОТИВ ПОДГОНКИ

Ваши запреты принимаю полностью. Добавляю механику, которая делает их проверяемыми.

### 11.1 Разделение данных — до первого прогона

| Кусок | Назначение | Правило |
|---|---|---|
| **DEV** | отладка харнесса | смотреть можно сколько угодно; результаты **не являются** результатами |
| **CALIBRATION** | настройка baseline C | смотреть можно; промпт Claude здесь **не трогается** |
| **HELD-OUT** | финальная проверка | **один прогон. Один.** До него не открывается |
| **FORWARD** | shadow в реальном времени | главный источник истины |

### 11.2 Предрегистрация

**До** первого прогона на HELD-OUT письменно фиксируется: гипотеза, главная метрика,
минимальная выборка, порог успеха, правило остановки. Файл коммитится с датой.

Без предрегистрации любой положительный результат необъясним: всегда остаётся вопрос,
не выбрана ли метрика после того, как стали видны цифры.

### 11.3 Промпт — это параметр

Каждая правка промпта после просмотра результатов **сжигает out-of-sample**. Через
двадцать «улучшений» получится промпт, подогнанный под период, и заметить это будет
нечем.

Поэтому: промпт версионируется в git, каждая версия датирована, результаты привязаны к
версии. Смена промпта = новый эксперимент, а не продолжение старого.

### 11.4 Параметры ACE

Фиксируются **до** тестов и не меняются по результатам. Изменение параметров ACE ради
результата — это подгонка индикатора под тест, и она обесценивает и то, и другое.

## 12. ФИНАЛЬНЫЙ ВЕРДИКТ — 9 ОТВЕТОВ

### 1. Может ли Claude быть самостоятельным trading decision engine поверх ACE?

**Как аналитический компонент — да.** Я могу принять снимок, разобрать контекст по
слоям, выдать структурированное решение и объяснить его. Для этого этапа (без
исполнения) этого достаточно.

**Как самостоятельная сущность — нет**, по причине из прошлого документа: я не процесс.
Цикл держит харнесс, я — шаг в нём.

### 2. Достаточно ли текущих данных ACE для качественных LONG/SHORT/HOLD?

**Нет.** Для `HOLD` — почти достаточно. Для `LONG`/`SHORT` — **нет**, потому что нет
цен уровней: **стоп поставить не на что**. А без стопа решение не является торговым.

Доступно 10 позиций из 43, ещё 8 — как события без уровней.

### 3. Какие данные ACE сейчас невозможно передать?

25 позиций — полный список в §1.4. Ключевые: **контрибуции компонентов, WHAT CHANGED,
статические POC/VAH/VAL, цены свингов, уровни BOS/CHoCH/MSS, цена свипа, границы FVG,
состояние AMT, IB/OR, dealing range, premium/discount, delta, слой L1/L2/L3, ATR.**

### 4. Нужно ли менять ACE?

**Для baseline A и B — нет.** Данных хватает, можно начинать завтра.

**Для проверки гипотезы D — да, иначе никак.** Альтернатива только одна: порт в Python.
Третьего варианта нет — значение, которое не плотится, не выходит наружу ничем.

Минимальная правка — **аддитивный блок числовых плотов**: ноль изменений в расчётах,
ноль в скоринге, ноль новых концепций, визуально ничего не меняется. **Я её не внёс.**
Решение ваше.

### 5. Какие 3–5 подходов естественно следуют из ACE?

Ротация в балансе · Acceptance breakout · Sweep + CHoCH разворот · VWAP reclaim /
z-score экстремум · Ретест FVG после displacement. Детали и режимы — §8.1.

### 6. Есть ли признаки потенциального edge?

**Признаки — да. Доказательств — ни одного.**

Аргумент «за», единственный содержательный: ACE строит **контекст**, а не сигнал, и
делает это честно (NO DATA ≠ NEUTRAL, разделение факта и интерпретации, проверенное
отсутствие repaint). Это лучшая стартовая позиция, чем у большинства индикаторных
систем, — там обычно ломается уже фундамент.

Аргументы «против»: edge самого ACE не измерен ни разу; аддитивный скоринг структурно
слаб в тренде (§8.3); издержки определённы, преимущество гипотетично; исторический
канал проверки для меня заражён (§9.3).

### 7. Как доказать или опровергнуть edge?

Baseline C на CALIBRATION → предрегистрация → один прогон HELD-OUT → forward/shadow.
Парное сравнение на одних барах, bootstrap-интервал **разницы** C и D. Сотни решений,
не десятки. Протокол — §9, дисциплина — §11.

### 8. Может ли Claude добавлять ценность поверх механического ACE?

**Гипотеза, а не факт.** Наиболее вероятное место — то, где формула структурно слаба:
**распознавание режима** (§8.3) и **отказ при противоречии слоёв**.

Наименее вероятное — выбор точек входа: это арифметика по уровням, и механика делает её
лучше, дешевле и одинаково.

Формулировка, которую я применяю к себе: **если я не обыгрываю C значимо — я в этой
системе лишний**, и правильным продуктом будет C. Это нормальный исход, и считать его
надо вероятным заранее.

### 9. Минимальный MVP
