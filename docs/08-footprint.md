# request.footprint() — проверка по актуальной документации (сентябрь 2026)

> **Статус предыдущего аудита: ОПРОВЕРГНУТ ЧАСТИЧНО.**
> В `01-feasibility.md` было заявлено, что footprint, buy/sell volume, delta и volume imbalances в Pine невозможны. **Это утверждение устарело.** В январе 2026 TradingView добавил `request.footprint()` в Pine Script v6. Ниже — проверенные по официальной документации факты и то, что именно меняется в архитектуре ACE.

Источник: официальный Pine Script® User Manual, раздел *Concepts → Other timeframes and data → `request.footprint()`*, плюс Help Center «Volume footprint charts: a complete guide» и анонс в блоге TradingView.

---

## 1. API (подтверждено дословно по документации)

```
request.footprint(ticks_per_row, va_percent, imbalance_percent) → series footprint
```

| Параметр | Тип | Описание |
|---|---|---|
| `ticks_per_row` | **simple int**, обязательный | Высота строки в тиках: `ticks_per_row × syminfo.mintick`. Определяет число строк в баре |
| `va_percent` | simple float, опц. | Процент общего объёма для Value Area. **Default 70** |
| `imbalance_percent` | simple float, опц. | Порог дисбаланса между соседними строками. **Default 300** (объём должен превышать противоположный в 3 раза) |

### Методы `footprint.*()`
| Метод | Возвращает |
|---|---|
| `total_volume()` | float — суммарный объём бара |
| `buy_volume()` | float — суммарный «покупной» объём |
| `sell_volume()` | float — суммарный «продажный» объём |
| `delta()` | float — дельта (buy − sell) |
| `poc()` | `volume_row` — строка Point of Control |
| `vah()` | `volume_row` — строка Value Area High |
| `val()` | `volume_row` — строка Value Area Low |
| `rows()` | `array<volume_row>` — все строки, **отсортированы по возрастанию цены** |
| `get_row_by_price(price)` | `volume_row` — строка, содержащая цену |

### Методы `volume_row.*()`
| Метод | Возвращает |
|---|---|
| `up_price()` / `down_price()` | float — верхняя / нижняя граница строки |
| `buy_volume()` / `sell_volume()` / `total_volume()` | float |
| `delta()` | float — дельта строки |
| `has_buy_imbalance()` / `has_sell_imbalance()` | bool — по порогу `imbalance_percent` родительского footprint |

**Определение imbalance (дословно):** buy imbalance — если «buy» объём строки превышает «sell» объём **строки ниже** на заданный процент; sell imbalance — если «sell» объём строки превышает «buy» объём **строки выше**. То есть диагональное сравнение, как в классическом footprint.

## 2. Ограничения — критичные для архитектуры

### 2.1. 🔴 Только Premium / Ultimate
Дословно: *«Volume footprints are available exclusively to users who have a Premium or Ultimate plan. Accounts with lower-tier plans **cannot use scripts** that request volume footprint data.»*

Это **не** «функция вернёт na» — это «скрипт нельзя использовать». Следствие: **само наличие `request.footprint()` в коде закрывает индикатор для Basic/Essential/Plus.** Это вопрос дистрибуции, а не техники, и он вынесен на ваше решение (см. §5).

### 2.2. 🔴 Ровно ОДИН footprint-запрос на скрипт
Дословно: *«Scripts cannot perform more than one footprint request... If a script contains multiple calls to this function, it raises a runtime error.»*

Более того: любой `request.security()` / `request.security_lower_tf()`, чьё выражение зависит от `footprint`/`volume_row`, **тоже засчитывается** как footprint-запрос, потому что компилятор копирует весь код в контекст запроса. Ошибка возникает, если выходы скрипта зависят более чем от одного footprint-запроса.

**Следствия для ACE:**
- `ticks_per_row` — **один глобальный параметр**. Нельзя иметь «грубый footprint для сессии» и «точный для текущего бара» одновременно.
- Нельзя одновременно брать footprint текущего ТФ и footprint дневного ТФ. Надо выбирать. Наш выбор — **текущий ТФ** (агрегацию по сессии мы делаем сами, см. §3).
- Запрос счётчика: лимит 40 уникальных `request.*()` (64 на Ultimate) — у нас их единицы, не проблема.

### 2.3. ⚠️ «Repainting by design»
Footprint строится из данных младших интервалов, и **глубина доступной гранулярности падает с возрастом бара**:
- intraday: 1 tick (professional plans) → 1 second → 1 minute → 60 minutes
- daily: 1 minute → 60 minutes
- weekly / monthly: 60 minutes

Help Center прямо называет это *repainting by design*: свежие бары считаются по мелкому интервалу, старые — по грубому. **Историческая картинка footprint может отличаться при перезагрузке графика**, потому что меняется доступная гранулярность.

Это прямо конфликтует со стандартом проекта «no repainting». Решение — не запрет, а **явное разделение и маркировка** (см. §4).

### 2.4. ⚠️ Buy/Sell — это НЕ bid/ask агрессор
Дословно: *«a volume footprint categorizes volume values from lower timeframes as "buy" (upward) or "sell" (downward) **based on intrabar price action**»*.
Help Center уточняет: объём считается «buy», если close подбара выше его open; «sell» — если ниже; ничья разрешается сравнением с close предыдущего подбара.

**Это тот же класс прокси, что наши D1/D2 — просто вычисленный на стороне сервера и на гораздо более мелких данных (вплоть до тика).** Это не дельта по агрессору из bid/ask.

Практический вывод: **исходный вердикт «настоящей дельты нет» остаётся верным по существу.** Неверным было утверждение, что *этих данных нет в Pine*. Они есть, они качественные, но это классифицированный по направлению цены объём, а не order flow по стакану. В дашборде подписываем честно: `Δ (TV footprint, price-direction classified)`.

### 2.5. ⚠️ Расхождение с `volume` на TF ≥ 1D
Дословно: на таймфреймах ≥ «1D» total_volume footprint'а может **существенно** отличаться от переменной `volume`, потому что EOD-фиды включают блочные и OTC-сделки, а интрадей-фиды — нет. Значит, нельзя смешивать footprint-объём и `volume` в одной формуле на дневках+.

### 2.6. `na` при отсутствии данных
`request.footprint()` возвращает `na`, если footprint для бара недоступен. Методы `footprint.*()` **не принимают `na`** в параметре `id` → каждый вызов обязан быть защищён проверкой. Это ровно наш паттерн `VALID / INVALID`.

## 3. Что меняется в архитектуре ACE

### 3.1. Уровни источников данных профиля — теперь 4 реальных

| Уровень | Источник | Точность | Требования |
|---|---|---|---|
| **L0** | OHLCV, `close` only (M1) | низкая | любой план |
| **L1** | Bar-based distribution (M2/M3) | средняя | любой план |
| **L2** | `request.security_lower_tf()` (M4) | высокая | любой план, глубина LTF ограничена |
| **L3** | **`request.footprint()`** | **максимальная из доступных** | **Premium/Ultimate** |

**L3 даёт то, чего не давал ни один предыдущий уровень:** готовые строки с раздельным buy/sell объёмом, дельтой по строке и флагами дисбаланса — то есть вход в Profile Engine **и** в Volume/Order Flow Engine одновременно.

### 3.2. Как L3 встраивается в Profile Engine

Важно: `footprint` — это **профиль одного бара**, а нам нужен профиль сессии/периода. Поэтому footprint не заменяет наш Profile Engine, а становится **лучшим источником вклада бара**:

```
для каждого бара:
    fp = request.footprint(ticksPerRow, vaPct, imbPct)
    если fp не na:
        для каждой row из fp.rows():
            центр = (row.up_price() + row.down_price()) / 2
            добавить row.total_volume() в наш бин по центру
            добавить row.buy_volume()  в binVolUp
            добавить row.sell_volume() в binVolDn
        model = "FOOTPRINT"
    иначе:
        откат на L2 → L1 (вклад бара по модели M4/M3)
        model = "LTF" / "BAR"
```

Это сохраняет всю нашу архитектуру (add-only накопители, POC/VA/HVN/LVN, developing-значения, предыдущие профили) и просто **повышает качество входных данных**. Наш сессионный POC/VAH/VAL считается по нашему алгоритму — а `fp.poc()/vah()/val()` используются отдельно как **побарные** значения и как эталон для валидации в P1.

**Важная деталь сетки:** чтобы не терять точность при перекладывании строк footprint в наши бины, ширина нашего бина должна быть **кратна** `ticks_per_row × mintick`. Добавляется input `Align bins to footprint rows` (default ON), который подгоняет сетку.

### 3.3. Что теперь получает Volume / Order Flow Engine

Было (только прокси D1/D2/D3): RVOL, грубая кумулятивная дельта.
Стало при L3:
- дельта бара (`fp.delta()`) — серверная классификация на тиковых/секундных данных;
- кумулятивная дельта сессии;
- дельта по каждому ценовому уровню (`row.delta()`) — то есть **Delta Profile**, а не только объёмный;
- **volume imbalances** (`has_buy_imbalance` / `has_sell_imbalance`) — новый объективный FACT-примитив;
- стеки дисбалансов (N подряд идущих строк с дисбалансом в одну сторону) — классический footprint-сигнал, формализуется тривиально;
- **unfinished auction** (дисбаланс/объём на крайней строке бара) — объективно детектируемо.

Эти примитивы становятся **FACT**, и Volume-компонент scoring-движка получает реальное содержание вместо слабого прокси. Пересматриваю его вес по умолчанию: `0.5 → 1.0` при активном L3 (при L0–L2 остаётся 0.5).

### 3.4. Новые FACT-примитивы в списке

Добавляются в FACT-слой: `bar delta`, `cumulative session delta`, `delta per price level`, `buy/sell imbalance rows`, `imbalance stacks`, `unfinished auction`, `footprint POC/VAH/VAL (per bar)`.
Остаются в INTERPRETATION: «absorption», «поглощение крупным игроком», «кто именно покупал» — эти выводы из price-direction-классификации **не следуют** и делаться не будут.

## 4. Repainting: новая строка стандарта проекта

Footprint нарушает наше правило «no repainting» — но не через lookahead, а через **недетерминированность гранулярности во времени**. Вводим третью категорию честности:

| Категория | Определение | Пример |
|---|---|---|
| Repaint (запрещено) | значение закрытого бара меняется из-за логики скрипта | использование будущих баров |
| Lag / backpainting (документируется) | значение не меняется, но известно позже | pivot, Order Block |
| **Source drift (новое, документируется)** | значение закрытого бара может измениться при перезагрузке, потому что **поставщик данных** меняет гранулярность | **footprint**, частично LTF |

Правила для L3 в ACE:
1. L3 **никогда не включён по умолчанию** — только явным выбором пользователя.
2. При активном L3 в дашборде обязательна строка `PROFILE DATA: FOOTPRINT — source drift possible on reload`.
3. Компоненты scoring, питающиеся от L3, помечаются в разбивке символом `~` (например `Volume ~+0.70`), чтобы отличать их от полностью детерминированных.
4. Правило `Confirm on bar close = ON` остаётся и для L3.
5. В `REPAINT-TEST-REPORT.md` появляется отдельный тест: сравнение значений до и после перезагрузки графика на исторических барах.

## 5. ⚠️ Решение, которое требуется от вас (влияет на P7, не на P0/P1)

Наличие `request.footprint()` в коде **блокирует скрипт для Basic/Essential/Plus**. Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Один скрипт с footprint** | максимум функциональности, одна кодовая база | недоступен всем, кроме Premium/Ultimate |
| **B. Два билда из одного исходника**: `ACE` (L0–L2, все планы) и `ACE Pro` (L0–L3, Premium+) | максимальный охват; L3 — честный апгрейд | две публикации, синхронизация версий |
| **C. Только L0–L2** | работает у всех, полностью детерминирован | отказ от лучших доступных данных |

**Моя рекомендация — B.** Именно поэтому P0 строится так, что весь L3 изолирован в **одном помеченном регионе** (`//#region L3 FOOTPRINT ADAPTER ... //#endregion`) с единственной точкой входа `fpBarContribution()`. Удаление этого региона даёт валидный билд для всех планов без единой правки в остальных модулях. Решение можно принять позже — архитектура его не блокирует.
