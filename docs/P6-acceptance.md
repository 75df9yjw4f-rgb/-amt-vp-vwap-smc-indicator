## 1. Алгоритмические определения

### Imbalance

| Понятие | Определение |
|---|---|
| **FVG (бычий)** | `low[0] > high[2]` → зона `[high[2], low[0]]` |
| **FVG (медвежий)** | `high[0] < low[2]` → зона `[high[0], low[2]]` |
| **FVG size** | высота зоны; трекается только при `size ≥ minFvgAtr × ATR` |
| **Mitigation** | доля зоны, пройденная ценой: бычья заполняется сверху `(top − min(low, top)) / span`, медвежья снизу `(max(high, bot) − bot) / span`. Значение **монотонно не убывает** |
| **Закрытие зоны** | по выбранному правилу: `Touch` (`mit > 0`) · `50%` (`mit ≥ 0.5`) · `Full` (`mit ≥ 1`) |
| **Displacement** | `abs(close − open) ≥ dispBodyAtr × ATR`, **и** (если `dispNeedsFvg`) на этом баре образовался FVG |

**Конвенция по displacement — важная оговорка.** Во многих описаниях крупная свеча стоит **в середине** тройки. Проверить это на баре `t` можно только зная бар `t+1` — то есть будущее. Поэтому у нас displacement-бар — **последний** бар тройки: разрыв между `high[2]` и `low[0]` полностью сформирован уже на текущем закрытии. Это детектируемо в реальном времени, и именно это делает код.

### Liquidity

| Понятие | Определение |
|---|---|
| **Уровень ликвидности** | подтверждённый свинг; при совпадении с существующим уровнем в пределах `eqTol × ATR` и `eqMaxGap` баров — сливается с ним, счётчик касаний растёт |
| **Equal High / Low** | уровень с `touches ≥ 2` |
| **Buy-side liquidity** | уровни выше цены (максимумы). **Позиционный термин, не направленный** |
| **Sell-side liquidity** | уровни ниже цены (минимумы) |
| **Пулы** | EQH/EQL + экстремумы предыдущего дня |
| **Sweep (базовый)** | для максимума: `high > level ∧ close < level` **на одном баре**. Зеркально для минимума |
| **Sweep (+CHoCH)** | sweep помечается как **pending**, подтверждается позже — на баре, где реально случилось структурное событие противоположного направления; истекает через `sweepConfirmBars` |

## 2. FACT vs INTERPRETATION — где проходит граница

Это потребовало **рефакторинга уже написанного кода**, и стоит объяснить почему.

Первая версия считала в Liquidity Engine `liqRaw = −lastSweepSide × strength`, а в Imbalance Engine `imbRaw = imbUpScore − imbDnScore`. Формально работает — но это **уже интерпретация внутри FACT-движка**: решение «снятие sell-side ликвидности идёт в плюс» никак не следует из данных, это конвенция.

Переделано:

| Слой | Что выдаёт |
|---|---|
| **Liquidity Engine (FACT)** | `lastSweepSide` (+1 снята buy-side / −1 sell-side), `sweepStrength` (затухание по возрасту), `poolAboveProx`, `poolBelowProx`, `eqHighCount`, `eqLowCount`, `nearestAbove`, `nearestBelow` — **величины и сторона, без знака вклада** |
| **Imbalance Engine (FACT)** | `imbUpScore`, `imbDnScore` (величины близости незакрытых гэпов с каждой стороны), `imbActive`, мит-доля по каждой зоне — **две магнитуды, без вычитания** |
| **Context Engine (INTERPRETATION)** | composes the signs: sell-side sweep → плюс; незакрытый гэп под ценой → плюс; пул притягивает цену к себе |

Конвенции знака теперь собраны в одном месте, прокомментированы прямо в коде и являются ровно той частью, с которой пользователь может обоснованно не согласиться.

**Отдельно про альтернативу для FVG.** Мы используем support/resistance-прочтение: незакрытый бычий гэп **под** ценой = поддержка, плюс. Существует равно защитимая противоположная конвенция: незакрытый гэп — это магнит, и он должен давать знак **к себе**. Она не отброшена молча — она указана здесь и в комментарии кода.

### NO DATA ≠ NEUTRAL — три разных состояния

P6 даёт точную иллюстрацию, зачем нужно различение:

| Состояние | Значение | Почему |
|---|---|---|
| Зон не отслеживается вообще | **NO DATA** | отсутствие свидетельства |
| Зоны есть, но ни одной рядом с ценой | **valid, raw = 0** | свидетельство есть и оно говорит «ничего направленного» |
| Уровней ликвидности нет | **NO DATA** | — |
| Уровни есть, sweep'а не было | **valid**, слабый вклад от пулов | — |

Первое и второе — разные вещи, и дашборд их различает.

## 3. Sweep и будущие данные (проверено отдельно, по вашему требованию)

**Базовое правило sweep использует ровно один бар:**
```
took = isHigh ? (high > level and close < level)
              : (low  < level and close > level)
```
`high`, `low`, `close` — текущий бар. `level` — сохранённое состояние из прошлого. **Обращений вперёд нет ни одного.**

**Режим «требуется CHoCH» тоже не смотрит вперёд.** Реализация:
1. На баре sweep'а событие записывается как **pending** (`sweepPendBar/Side/Level`).
2. На каждом последующем баре проверяется, произошло ли **на этом баре** структурное событие противоположного направления (`takeDir == −sweepPendSide`).
3. Если да — sweep становится подтверждённым. Если прошло больше `sweepConfirmBars` — pending **истекает и отбрасывается**.

То есть подтверждение происходит на баре, где событие реально случилось. Ничего не «дописывается назад» в бар, который ещё не закрылся.

**Визуальная оговорка:** подтверждённый sweep рисуется на баре, где он произошёл, хотя подтверждение пришло позже. Это **backpainting**, не repainting. Пока sweep ждёт подтверждения, он помечен на графике как `sweep?` жёлтым — то есть незавершённость видна, а не скрыта.

**Гейт по закрытию бара:** вся детекция обёрнута в `liqBarOk = confirmClose ? barstate.isconfirmed : true`.

### Бюджет графических объектов — найдена и исправлена реальная проблема

Лимит боксов — **500 жёстко**. Гистограммы профилей и зоны FVG рисуются боксами. При `bins = 300` для текущего и предыдущего профиля плюс 200 FVG получалось **≈ 800 боксов** — превышение лимита.

Введён общий бюджет (секция `12c. DRAWING BUDGET`):
```
BOX_LIMIT = 500, BOX_RESERVE = 20
fvgBoxBudget  = showFvg ? maxZones : 0
profBoxBudget = 480 − fvgBoxBudget
curBoxBudget  = 60% профильного бюджета (100%, если предыдущий профиль выключен)
```
Если гистограмма не помещается — **она не рисуется, и дашборд говорит об этом** строкой `Histogram hidden: bins exceed the box budget (N)`. Нарисовать половину профиля было бы хуже, чем не нарисовать ничего.

### Итоговый бюджет объектов при дефолтах

| Тип | Использовано | Лимит |
|---|---|---|
| Boxes | 50 (профиль) + 25 (FVG) = **75** | 500 |
| Lines | 6 профиль + 5 структура + 20 события + 30 ликвидность = **61** | 500 |
| Labels | 30 свинги + 20 события + 30 EQH/EQL + 2 sweep = **82** | 500 |
| Plots | **18** | 64 |

При максимальных настройках (Pro, `bins=300`, `maxZones=200`, `maxLiqLevels=100`): боксы 280+200 = 480, линии 131, лейблы 222 — в пределах.

## 8. Known Limitations

1. **Order Block не реализован.** Его не было в вашем списке на P6. Input `Show Order Blocks` теперь **по умолчанию выключен**, переименован в `Order Blocks (not implemented yet)`, тултип начинается со слов «NOT IMPLEMENTED AS OF P6», и debug-панель пишет `order blocks: not implemented (input is inert)`. Неработающий переключатель, выглядящий рабочим, — это тихая ложь, поэтому он помечен со всех сторон.

2. **Уровни ликвидности наследуют pivot lag.** Они строятся из подтверждённых свингов, а значит становятся известны на `swingLen` баров позже, чем произошли. Sweep такого уровня детектируется честно в реальном времени, но сам уровень появился с задержкой.

3. **Sweep с подтверждением через CHoCH — backpainting.** Метка ставится на баре прокола, хотя подтверждение пришло позже. Смягчено тем, что pending-состояние видно как `sweep?`.

4. **Знаковые конвенции спорны — обе.** Sell-side sweep → плюс и незакрытый гэп под ценой → плюс. Для FVG противоположная конвенция (гэп как магнит) равно защитима. Обе задокументированы в коде; при желании выносится в input.

5. **Пулы — только EQH/EQL и экстремумы прошлого дня.** Недельные экстремумы, IB и границы предыдущего профиля в пул не включены (IB — это P4). Расширяется тривиально.

6. **Слияние уровней усредняет цену.** При слиянии касаний уровень становится средним. Альтернатива — держать точный экстремум. Усреднение устойчивее к шуму, но формально «уровень» перестаёт совпадать с реальным хаем.

7. **Вытеснение зон может убрать живую зону.** При переполнении сначала удаляются закрытые, но если все активны — уходит старейшая, даже если она значимая.

8. **Гистограмма профиля может быть скрыта бюджетом боксов.** Это осознанный размен: лучше не нарисовать, чем нарисовать частично. Дашборд сообщает.

9. **Офлайн-компиляции Pine не существует** — E1/E2 подтверждаете вы. Без изменений с P0.
